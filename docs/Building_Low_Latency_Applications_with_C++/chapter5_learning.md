> 教材：《Building Low Latency Applications with C++》  
> 阶段：第三阶段（第 5–7 章）  
> 目标：从高层架构出发，理解电子交易生态系统的整体拓扑、组件划分、交互设计，以及低延迟原则如何在架构层面落地。

7. 无锁队列在交易所组件间通信中扮演什么角色？为什么撮合引擎、行情发布器、订单网关是独立线程？

## 二、为什么要学这一章？

第四章构建了**可复用的基础组件**（线程、内存池、无锁队列、日志、socket）。  
第五章的作用是把这些组件**组织成一个完整的系统架构**：

- 从全局视角理解交易所和客户端的拓扑关系；
- 不再孤立地看"优化技巧"，而是看到每个组件在整体中的位置；
- 为后续第六、七章的代码实现建立清晰的架构蓝图。

> **核心思想**：架构设计决定了延迟的上限。先设计好组件边界、通信方式和数据流向，再去优化每个组件，才能达到全局最优。

## 三、学习路线（分 5 个小节）

### 第 1 小节：电子交易生态系统的整体拓扑

#### 5.1.1 简化版电子交易生态

书中构建的是一个**简化但准确**的电子交易生态系统模型。实际生产环境还有更多组件（历史数据采集、清算连接、后台处理、回测框架等），但本书聚焦**低延迟关键路径**。

#### 5.1.2 系统拓扑图

```
┌─────────────────── 交易所端（Exchange）───────────────────┐
│                                                              │
│  ┌──────────────┐  ┌──────────────────┐  ┌──────────────┐  │
│  │  撮合引擎    │  │  行情发布器      │  │  订单网关    │  │
│  │  Matching    │  │  Market Data     │  │  Order       │  │
│  │  Engine      │  │  Publisher       │  │  Gateway     │  │
│  │              │  │                  │  │  Server      │  │
│  │  订单簿维护  │  │  UDP 增量+快照   │  │  TCP 服务器  │  │
│  │  订单撮合    │  │  行情编码        │  │  FIFO 排序   │  │
│  └──────┬───────┘  └────────▲─────────┘  └──────▲───────┘  │
│         │  SPSC 队列        │   SPSC 队列       │  SPSC 队列│
│         └───────────────────┴───────────────────┘           │
└──────────────────────────────────────────────────────────────┘
          │ 网络                       │ UDP 组播      ▲ TCP
          ▼                           ▼               │
┌─────────────────── 客户端（Client）────────────────────────┐
│                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  行情消费器  │  │  交易引擎    │  │  订单网关    │      │
│  │  Market Data │  │  Trading     │  │  客户端      │      │
│  │  Consumer    │──▶  Engine      │──▶  Order GW    │──────┘
│  │              │  │              │  │  Client      │
│  │  UDP 订阅    │  │  订单簿      │  │  TCP 客户端  │
│  │  快照同步    │  │  策略/风控   │  │  协议编解码  │
│  └──────────────┘  └──────────────┘  └──────────────┘
└──────────────────────────────────────────────────────────────┘
```

#### 5.1.3 各组件一览

| 位置 | 组件 | 职责 | 通信协议 |
|---|---|---|---|
| 交易所 | **撮合引擎（Matching Engine）** | 维护订单簿、匹配买卖订单 | 内部 SPSC 队列 |
| 交易所 | **行情发布器（Market Data Publisher）** | 发布订单簿变更和成交信息 | UDP 组播（增量 + 快照） |
| 交易所 | **订单网关服务器（Order Gateway Server）** | 接受客户端连接、路由订单请求 | TCP |
| 客户端 | **行情消费器（Market Data Consumer）** | 订阅 UDP 行情、解码、同步 | UDP |
| 客户端 | **交易引擎（Trading Engine）** | 订单簿重建、特征计算、策略决策 | 内部 |
| 客户端 | **订单网关客户端（Order Gateway Client）** | 连接交易所、发送订单、接收回报 | TCP |

> **核心要点**：交易所端的三个组件（撮合引擎、行情发布器、订单网关）是**独立线程**，通过**无锁 SPSC 队列**通信。这种设计让每个组件在行情爆发时独立全速运行，互不阻塞。

### 第 2 小节：撮合引擎（Matching Engine）设计

#### 5.2.1 撮合引擎的职责

撮合引擎是交易所最核心的组件，负责：

1. **接收订单请求**：来自订单网关的客户端请求（新单、改单、撤单）；
2. **维护限价订单簿**：按价格/时间优先级排列所有未成交订单；
3. **撮合订单**：当新订单价格与对侧已有订单交叉时，执行撮合。

#### 5.2.2 限价订单簿（Limit Order Book）

限价订单簿按**价格-时间优先级**组织订单：

```
买方（Bids）—— 最高买价排最前          卖方（Asks）—— 最低卖价排最前
─────────────────────────────────      ─────────────────────────────────

@10.90: OrderId=1(20) ←优先            @11.00: OrderId=5(1)  ←优先
        OrderId=8(10)                          OrderId=6(5)
@10.80: OrderId=3(5)                    @11.10: OrderId=7(5)
        OrderId=2(20)                   @11.20: OrderId=9(10)
@10.70: OrderId=4(100)
```

> - **买盘从高到低**排列（买家愿意出更高的价格 → 更有竞争力）
> - **卖盘从低到高**排列（卖家愿意接受更低的价格 → 更有竞争力）
> - **同价格下按 FIFO**（先来的订单优先成交）

#### 5.2.3 术语定义

| 术语 | 含义 |
|---|---|
| **Limit Order（限价单）** | 指定价格和数量的订单，只能以该价格或更好的价格成交 |
| **Passive Order（被动订单）** | 未立即成交，停留在订单簿中的订单 |
| **Aggressive Order（主动订单）** | 价格与对侧订单交叉，能立即成交的订单 |
| **Bid（买价）** | 买方愿意支付的最高价格 |
| **Ask/Offer（卖价）** | 卖方愿意接受的最低价格 |
| **Spread（价差）** | Ask - Bid 之间的差额 |
| **TOB/BBO** | Top of Book / Best Bid and Offer，最优买价和卖价 |

#### 5.2.4 订单簿操作示例

**初始状态**：

```
Bids:                          Asks:
A: Buy  20 @ 10.90            B: Sell 10 @ 11.00
A: Buy  10 @ 10.80            C: Sell 5  @ 11.00
B: Buy  5  @ 10.80            B: Sell 5  @ 11.10
C: Buy  100 @ 10.70
```

**场景 1：C 发送 Sell 50 @ 10.90（主动卖单匹配买单）**

```
匹配过程：
  OrderId=1 的 20 股全部成交（移除）
  OrderId=8 的 10 股全部成交（移除）
  OrderId=4 的 20 股成交（剩余 80 股）

结果：
  Bids:                        Asks:
  C: Buy  80 @ 10.90          B: Sell 1  @ 11.00
  A: Buy  5  @ 10.80          C: Sell 5  @ 11.00
  B: Buy  20 @ 10.80          B: Sell 5  @ 11.10
```

**场景 2：A 发送 Buy 10 @ 11.00（主动买单匹配卖单）**

```
匹配过程：
  OrderId=5 的 1 股全部成交（移除）
  OrderId=6 的 5 股全部成交（移除）
  剩余 4 股未成交（停留为被动订单）

结果：
  Bids:                        Asks:
  A: Buy  4  @ 11.00          B: Sell 5  @ 11.10
  C: Buy  80 @ 10.90
  ...
```

#### 5.2.5 订单修改规则

| 操作 | 对 FIFO 优先级的影响 |
|---|---|
| **减少数量** | **不改变**优先级，保持原位 |
| **增加数量** | **失去优先级**，排到同价格队尾 |
| **修改价格** | 等同于**撤单 + 新单**，重新排队 |
| **修改价格 + 数量** | 等同于**撤单 + 新单** |

#### 5.2.6 撮合引擎的线程模型与通信

```
订单网关响应 ──▶ ┌─────────────────┐ ──▶ 行情更新
  (SPSC)        │  Matching Engine │      (SPSC)
                │  (独立线程)      │
订单网关请求 ──▶ │                 │ ──▶ 客户端回报
  (SPSC)        └─────────────────┘      (SPSC)
```

| 设计要点 | 说明 |
|---|---|
| **独立线程** | 撮合引擎独占一个 CPU 核心，不被其他组件干扰 |
| **双向队列** | 订单网关 → 撮合引擎（请求），撮合引擎 → 订单网关（回应 + 成交通知） |
| **无锁 SPSC** | 使用第四章实现的 lock-free queue，避免内核态切换 |
| **内存池** | 订单对象从预分配内存池获取，避免 `new/delete` |

#### 5.2.7 订单簿的数据结构选择

| 需求 | 数据结构 | 原因 |
|---|---|---|
| 买卖盘排序 | 有序容器（按价格排序） | 撮合从最优价格开始 |
| 同价格 FIFO | 双向链表 | 高效的在头部/尾部插入删除 |
| 按价格查找 | HashMap（价格 → 价格档位） | O(1) 查找特定价格档位 |
| 按订单 ID 查找 | HashMap（订单 ID → 订单对象） | O(1) 查找/修改/删除特定订单 |

> 设计原则：**避免动态内存分配**。订单对象从内存池获取，节点来自预分配池，热路径上零 `new`/`delete`。

### 第 3 小节：行情发布器（Market Data Publisher）设计

#### 5.3.1 行情数据的两重角色

交易所向市场参与者发布两类信息：

| 类型 | 渠道 | 内容 | 受众 |
|---|---|---|---|
| **公共行情** | 行情发布器（UDP 组播） | 订单簿变更、成交信息 | **所有**市场参与者 |
| **私有通知** | 订单网关（TCP） | 订单状态更新、成交回报 | **只有**该订单的所属客户端 |

> 关键区别：公共行情隐藏了"哪个客户"的信息（公平性），私有通知只发给订单拥有者。

#### 5.3.2 行情消息类型

书中将市场数据消息分为以下几类：

| 消息类型 | 含义 | 典型字段 |
|---|---|---|
| **Order Add** | 新订单进入订单簿 | 品种 ID、订单 ID、价格、方向、数量、优先级 |
| **Order Modify** | 订单被修改（价格/数量变化） | 类似 Order Add，但含修改后状态 |
| **Order Delete** | 订单被移除（成交/撤单） | 品种 ID、订单 ID |
| **Trade** | 发生了撮合成交 | 品种 ID、主动方方向、成交价、成交量 |
| **Market State** | 市场状态变更 | 状态（Closed / PreOpen / Opening / Trading） |
| **Instrument Update** | 品种元数据变更 | 最小价格变动单位(tick size)、乘数等 |

> 行情协议的常见格式：FIX（TAG=VALUE 文本格式，灵活但冗余）、FAST（FIX 的压缩版）、EOBI/SBE（二进制打包结构，最快解码）。本书使用**自定义二进制打包协议**。

#### 5.3.3 增量流与快照流

这是行情设计中最重要的概念之一：

| 流类型 | 特点 | 用途 |
|---|---|---|
| **增量流（Incremental）** | 只推送订单簿的**变化**（新单/改单/撤单/成交） | 正常运行时维护订单簿，带宽低、延迟低 |
| **快照流（Snapshot）** | 推送整个订单簿的**完整快照** | 启动时初始化、丢包后恢复 |

**为什么需要两套流？**

UDP 组播虽然延迟低，但不保证可靠到达。如果客户端丢了一个增量包，订单簿就与实际状态不一致了。恢复流程：

```
1. 检测丢包（序列号不连续）
2. 清空本地订单簿
3. 订阅快照流，等待完整快照到达
4. 期间缓存在此之后的增量更新
5. 从快照重建完整订单簿 → 应用缓存的增量更新 → 同步完成
6. 退订快照流，只依赖增量流
```

#### 5.3.4 行情发布器的子组件

```
Market Data Publisher
├── Market Data Encoder（行情编码器）
│   ├── 从撮合引擎消费订单簿变更
│   ├── 转换为行情协议格式
│   ├── 发布到 UDP 增量组播流
│   └── 同时推送给 Snapshot Synthesizer
│
└── Snapshot Synthesizer（快照合成器）—— 独立线程
    ├── 消费编码后的增量更新
    ├── 合成完整订单簿快照
    ├── 附加快照序列号（上次增量流序列号）
    └── 周期性发布到 UDP 快照组播流
```

> 快照合成器是**独立线程**，不阻塞增量流的实时发布。它对延迟不敏感（本身就是延迟的、降采样的流）。

#### 5.3.5 为什么行情用 UDP 而不是 TCP？

| 考量 | UDP | TCP |
|---|---|---|
| 延迟 | 更低，无确认和重传 | 较高，需确认和重传 |
| 吞吐 | 更高，无 ACK 带宽开销 | 较低，有额外带宽开销 |
| 可靠性 | 不可靠，可能丢包 | 可靠，保证到达和顺序 |
| 扩展性 | 组播：一份数据所有订阅者同时收到 | 单播：每条连接独立发送 |
| 解决方案 | 快照流 + 序列号提供恢复机制 | 天然可靠 |

### 第 4 小节：订单网关（Order Gateway）设计

#### 5.4.1 订单网关的角色定位

订单网关是交易所和客户端之间的**双向通信桥梁**：

```
客户端 ←─ TCP ─→ 订单网关服务器 ←─ SPSC 队列 ─→ 撮合引擎
```

| 方向 | 内容 |
|---|---|
| 客户端 → 订单网关 | 新单、改单、撤单请求 |
| 订单网关 → 撮合引擎 | 翻译为内部格式的订单请求 |
| 撮合引擎 → 订单网关 | 订单处理结果、成交通知 |
| 订单网关 → 客户端 | 订单状态更新、成交回报 |

#### 5.4.2 订单网关的子组件

```
Order Gateway Server
├── TCP Connection Manager（连接管理器）
│   ├── 监听并接受客户端的 TCP 连接
│   ├── 管理活跃连接列表
│   ├── 检测断开并清理
│   └── 将撮合引擎的回应路由到正确的客户端连接
│
├── FIFO Sequencer（FIFO 排序器）
│   └── 确保多条客户端连接的请求按到达时间顺序转发
│
└── Protocol Encoder/Decoder（协议编解码器）
    ├── 将客户端请求（交易所协议）解码为撮合引擎内部格式
    └── 将撮合引擎回应编码为交易所协议格式
```

#### 5.4.3 为什么订单网关用 TCP 而不是 UDP？

| 原因 | 说明 |
|---|---|
| **可靠性** | 订单一旦发出就不能丢失，必须保证送达 |
| **有序性** | 订单的顺序很重要（先发先处理），TCP 天然有序 |
| **双向通信** | 客户端同时发送请求和接收回应 |
| **连接状态** | 需要明确知道客户端是否在线 |

#### 5.4.4 FIFO Sequencer 的作用

公平性是交易所的核心原则。如果两个客户端同时发送订单，先到达交易所网关的应该先被处理：

```
Client A 连接 ──┐
                 ├── FIFO Sequencer ──▶ 撮合引擎（按到达时间排序）
Client B 连接 ──┘
```

这确保即使不同 TCP 连接的内核 buffer 处理有微小差异，最终转发给撮合引擎的顺序仍然是**到达交易所硬件的实际顺序**。

#### 5.4.5 生产环境中的附加功能（本书简化处理）

| 功能 | 说明 |
|---|---|
| 客户端认证（Logon） | 身份验证、密码检查 |
| 心跳（Heartbeat） | 检测连接存活，低活动期保持连接 |
| 应用层序列号 | 额外的可靠性保障，与 TCP 互补 |
| 负载均衡 | 多连接分散到不同订单网关实例 |

### 第 5 小节：客户端交易策略框架设计

#### 5.5.1 客户端系统的整体结构

```
┌──────────────── 客户端交易系统 ────────────────┐
│                                                  │
│  行情消费器 ──▶ 交易引擎（Trading Engine）──▶ 订单网关客户端  │
│  (UDP 订阅)    │  ├── 订单簿                      │  (TCP)
│  (快照同步)    │  ├── Feature Engine（特征引擎）    │
│  (协议解码)    │  ├── Trading Strategy（交易策略）   │
│                │  ├── Order Manager（订单管理器）    │
│                │  └── Risk Manager（风险管理器）    │
│                │                                  │
└──────────────────────────────────────────────────┘
```

#### 5.5.2 行情消费器（Market Data Consumer）

| 职责 | 说明 |
|---|---|
| **UDP 订阅** | 加入交易所行情组播地址 |
| **协议解码** | 将交易所行情格式解码为内部标准化格式 |
| **快照同步** | 启动/丢包时执行增量+快照同步流程 |
| **跨交易所标准化** | 不同交易所的格式统一为内部标准格式 |

**快照同步流程**：

```
Step 1: 清空订单簿，订阅快照流
Step 2: 继续收取增量流数据并缓存
Step 3: 收到完整快照 → 重建订单簿
Step 4: 将缓存的增量更新（从 snapshot 序列号之后开始）应用到订单簿
Step 5: 同步完成，退订快照流
```

#### 5.5.3 客户端订单簿

客户端也需要维护一份订单簿，但与交易所撮合引擎的订单簿有所不同：

| 差异点 | 交易所订单簿 | 客户端订单簿 |
|---|---|---|
| 知道订单所属方 | 知道每笔订单属于哪个客户 | 不知道（公有行情隐藏了客户 ID） |
| 实时性 | 实时 | 略微延迟（网络传输 + 解码） |
| 撮合功能 | 需要撮合 | 不需要撮合，只需更新 |
| 自有订单跟踪 | 不需要 | 通常需要知道自己的订单在 FIFO 队列中的位置 |

#### 5.5.4 Feature Engine（特征引擎）

特征引擎基于订单簿数据生成交易信号：

```
订单簿 ──▶ Feature Engine ──▶ 特征值 ──▶ 交易策略
              │
              ├── 市场公允价格（基于 TOB 价格和数量加权）
              ├── 买卖压力指标
              ├── 成交量异常检测
              └── 市场微观结构信号
```

> 本书只实现**最简特征引擎**：计算 TOB 加权公允价格和主动单相对 TOB 数量的比率。生产环境中特征引擎可以非常复杂，包含统计模型、机器学习等。

#### 5.5.5 PositionKeeper（仓位跟踪器）

| 职责 | 说明 |
|---|---|
| 处理成交记录 | 根据成交更新仓位 |
| 计算持仓 | 多空方向净持仓 |
| 计算 PnL | 已实现盈亏 + 未实现盈亏 |
| 持仓成本 | 加权平均成交价 |

#### 5.5.6 Order Manager（订单管理器）

Order Manager 是整个客户端策略框架中最复杂的组件之一，负责管理策略所有活跃订单的生命周期。

**核心职责**：

| 职责 | 说明 |
|---|---|
| 发送订单 | 将策略的订单请求编码并发送 |
| 管理状态 | 跟踪每个订单的状态（发送中/活跃/部分成交/已成交/已取消） |
| 处理 in-flight 冲突 | 撤单请求正在路上，但订单已被撮合 |
| 处理成交 | 部分/全部成交的状态更新 |
| 去重和序列号 | 应用层保证不重不漏 |

**In-Flight 冲突示例**：

```
时间线：
T1: 客户端发送 Cancel OrderId=5 的请求
T2: 同时，交易所匹配引擎收到了一个 Aggressive Buy，把 OrderId=5 撮合了
T3: Cancel 请求到达交易所 ──▶ OrderId=5 已不存在 ──▶ Cancel Reject

Order Manager 需要正确处理：
  - 收到 T2 的成交通知（来自行情或订单网关）
  - 收到 T3 的撤单拒绝
  - 知道这个订单已经不存在了，不能重复发出请求
```

#### 5.5.7 Risk Manager（风险管理器）

| 风险类别 | 具体指标 | 说明 |
|---|---|---|
| **订单量** | 单笔订单最大数量 | 防止"胖手指"错误 |
| **持仓** | 当前净持仓 | 直接决定市场风险暴露 |
| **最坏情况持仓** | 含所有活跃买单的潜在持仓 | 极端情况下的风险 |
| **盈亏** | 已实现 + 未实现盈亏 | 跟踪实际损失 |
| **交易量** | 累计交易量上限 | 防止算法失控 |
| **频率** | 订单/成交/亏损的滑动窗口统计 | 防止异常交易行为 |

> 实际系统中有**多层风控**：策略层、订单网关客户端层、清算经纪商后台层。本书实现策略层的基础风控。

#### 5.5.8 两种核心交易策略

| 策略类型 | 角色 | 订单类型 | 利润来源 |
|---|---|---|---|
| **Market Maker（做市商）** | 流动性提供者 | 双边挂单（同时挂买单和卖单） | 买卖价差 |
| **Liquidity Taker（流动性提取者）** | 流动性消费者 | 主动吃单 | 预测价格方向 |

**Market Maker**：
- 在最优买价和卖价附近各挂一个单
- 赚取 bid-ask spread
- 风险：逆向选择（价格朝不利方向移动时没来得及撤单）

**Liquidity Taker**：
- 基于信号/预测决定买卖方向
- 主动以对侧价格成交
- 风险：信号质量、延迟

## 五、常见误区与注意事项

| 误区 | 正确认识 |
|---|---|
| ❌ "撮合引擎就是订单簿" | ✅ 订单簿是撮合引擎内部维护的数据结构，撮合引擎还包含匹配逻辑、组件通信等 |
| ❌ "行情数据用 UDP 就不需要确认了" | ✅ 需要序列号 + 快照恢复机制来弥补 UDP 的不可靠性 |
| ❌ "客户端订单簿和交易所订单簿完全一样" | ✅ 客户端看不到订单所属方，并且有传输延迟 |
| ❌ "FIFO 排序器是无关紧要的组件" | ✅ 它保证了市场公平性——先到的订单先被处理 |
| ❌ "Feature Engine 必须很复杂" | ✅ 可以根据策略需求从简开始；本书只有两个简单特征 |
| ❌ "Order Manager 就是发单和收回报" | ✅ 它需要处理大量 in-flight 冲突情况（撤单 vs 撮合 etc.） |
| ❌ "风险控制会拖慢系统" | ✅ 合理的设计（独立线程、预计算）可以将风控延迟降到很低 |

## 八、本章核心金句

> "架构设计决定了延迟的上限——选对组件边界和通信方式，比事后优化代码更有价值。"

> "UDP 不是不负责——它有增量流的高效，也有快照流的兜底。"

> "订单簿是交易所的心脏，撮合引擎是心脏的起搏器。"

> "订单网关追求可靠性，行情发布追求速度——两者用不同的协议，服务于不同的目标。"

> "一个没有 FIFO 规则的交易所不是一个公平的市场。"

> "在低延迟交易中，每一微秒的架构设计决策，都以真金白银来衡量。"
