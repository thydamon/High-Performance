## 二、为什么要学这一章？

第四章构建了**可复用的基础组件**（线程、内存池、无锁队列、日志、socket）。  
第五章的作用是把这些组件**组织成一个完整的系统架构**：

- 从全局视角理解交易所和客户端的拓扑关系；
- 不再孤立地看"优化技巧"，而是看到每个组件在整体中的位置；
- 为后续第六、七章的代码实现建立清晰的架构蓝图。

> **核心思想**：架构设计决定了延迟的上限。先设计好组件边界、通信方式和数据流向，再去优化每个组件，才能达到全局最优。

## 三、学习路线（分 5 个小节）

### 第 1 小节：电子交易生态系统的整体拓扑

#### 5.1.1 简化版电子交易生态

书中构建的是一个**简化但准确**的电子交易生态系统模型。实际生产环境还有更多组件（历史数据采集、清算连接、后台处理、回测框架等），但本书聚焦**低延迟关键路径**。

#### 5.1.2 系统拓扑图

```
┌─────────────────── 交易所端（Exchange）───────────────────┐
│                                                              │
│  ┌──────────────┐  ┌──────────────────┐  ┌──────────────┐  │
│  │  撮合引擎    │  │  行情发布器      │  │  订单网关    │  │
│  │  Matching    │  │  Market Data     │  │  Order       │  │
│  │  Engine      │  │  Publisher       │  │  Gateway     │  │
│  │              │  │                  │  │  Server      │  │
│  │  订单簿维护  │  │  UDP 增量+快照   │  │  TCP 服务器  │  │
│  │  订单撮合    │  │  行情编码        │  │  FIFO 排序   │  │
│  └──────┬───────┘  └────────▲─────────┘  └──────▲───────┘  │
│         │  SPSC 队列        │   SPSC 队列       │  SPSC 队列│
│         └───────────────────┴───────────────────┘           │
└──────────────────────────────────────────────────────────────┘
          │ 网络                       │ UDP 组播      ▲ TCP
          ▼                           ▼               │
┌─────────────────── 客户端（Client）────────────────────────┐
│                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  行情消费器  │  │  交易引擎    │  │  订单网关    │      │
│  │  Market Data │  │  Trading     │  │  客户端      │      │
│  │  Consumer    │──▶  Engine      │──▶  Order GW    │──────┘
│  │              │  │              │  │  Client      │
│  │  UDP 订阅    │  │  订单簿      │  │  TCP 客户端  │
│  │  快照同步    │  │  策略/风控   │  │  协议编解码  │
│  └──────────────┘  └──────────────┘  └──────────────┘
└──────────────────────────────────────────────────────────────┘
```

#### 5.1.3 各组件一览

| 位置 | 组件 | 职责 | 通信协议 |
|---|---|---|---|
| 交易所 | **撮合引擎（Matching Engine）** | 维护订单簿、匹配买卖订单 | 内部 SPSC 队列 |
| 交易所 | **行情发布器（Market Data Publisher）** | 发布订单簿变更和成交信息 | UDP 组播（增量 + 快照） |
| 交易所 | **订单网关服务器（Order Gateway Server）** | 接受客户端连接、路由订单请求 | TCP |
| 客户端 | **行情消费器（Market Data Consumer）** | 订阅 UDP 行情、解码、同步 | UDP |
| 客户端 | **交易引擎（Trading Engine）** | 订单簿重建、特征计算、策略决策 | 内部 |
| 客户端 | **订单网关客户端（Order Gateway Client）** | 连接交易所、发送订单、接收回报 | TCP |

> **核心要点**：交易所端的三个组件（撮合引擎、行情发布器、订单网关）是**独立线程**，通过**无锁 SPSC 队列**通信。这种设计让每个组件在行情爆发时独立全速运行，互不阻塞。

### 第 2 小节：撮合引擎（Matching Engine）设计

#### 5.2.1 撮合引擎的职责

撮合引擎是交易所最核心的组件，负责：

1. **接收订单请求**：来自订单网关的客户端请求（新单、改单、撤单）；
2. **维护限价订单簿**：按价格/时间优先级排列所有未成交订单；
3. **撮合订单**：当新订单价格与对侧已有订单交叉时，执行撮合。

#### 5.2.2 限价订单簿（Limit Order Book）

限价订单簿按**价格-时间优先级**组织订单：

```
买方（Bids）—— 最高买价排最前          卖方（Asks）—— 最低卖价排最前
─────────────────────────────────      ─────────────────────────────────

@10.90: OrderId=1(20) ←优先            @11.00: OrderId=5(1)  ←优先
        OrderId=8(10)                          OrderId=6(5)
@10.80: OrderId=3(5)                    @11.10: OrderId=7(5)
        OrderId=2(20)                   @11.20: OrderId=9(10)
@10.70: OrderId=4(100)
```

> - **买盘从高到低**排列（买家愿意出更高的价格 → 更有竞争力）
> - **卖盘从低到高**排列（卖家愿意接受更低的价格 → 更有竞争力）
> - **同价格下按 FIFO**（先来的订单优先成交）

#### 5.2.3 术语定义

| 术语 | 含义 |
|---|---|
| **Limit Order（限价单）** | 指定价格和数量的订单，只能以该价格或更好的价格成交 |
| **Passive Order（被动订单）** | 未立即成交，停留在订单簿中的订单 |
| **Aggressive Order（主动订单）** | 价格与对侧订单交叉，能立即成交的订单 |
| **Bid（买价）** | 买方愿意支付的最高价格 |
| **Ask/Offer（卖价）** | 卖方愿意接受的最低价格 |
| **Spread（价差）** | Ask - Bid 之间的差额 |
| **TOB/BBO** | Top of Book / Best Bid and Offer，最优买价和卖价 |

#### 5.2.4 订单簿操作示例

**初始状态**（三位客户 A、B、C 各有若干订单）：

```
Bids（买单）:                   Asks（卖单）:
A: Buy  20 @ 10.90 (OrderId=1)  B: Sell 10 @ 11.00 (OrderId=5)
A: Buy  10 @ 10.80 (OrderId=2)  C: Sell 5  @ 11.00 (OrderId=6)
B: Buy  5  @ 10.80 (OrderId=3)  B: Sell 5  @ 11.10 (OrderId=7)
C: Buy 100 @ 10.70 (OrderId=4)
```

> **注意**：初始状态中，最优买价（最高出价）= 10.90，最优卖价（最低要价）= 11.00。因为 10.90 < 11.00，没有交叉，所以不发生撮合。

---

**中间变化**（在撮合之前，市场中发生了一系列操作）：

```
变化 1：A 发送新买单 Buy 10 @ 10.90
        → OrderId=8 新增，排在 OrderId=1 后面（同价 FIFO）

变化 2：B 发送新卖单 Sell 10 @ 11.20
        → OrderId=9 新增（卖单队尾）

变化 3：A 将 OrderId=2 的数量从 10 改为 20（增加数量）
        → 失去优先级，排到 @10.80 队尾（OrderId=3 后面）

变化 4：B 将 OrderId=5 的数量从 10 改为 1（减少数量）
        → 保留优先级，仍在 @11.00 排头

变化 5：C 将 OrderId=4 的价格从 10.70 改为 10.90（修改价格）
        → 等同于撤单+新单，排到 @10.90 队尾

变化 6：B 撤销 OrderId=9
        → 卖单被移除
```

**经过上述变化后，订单簿的"撮合前状态"**：

```
Bids（买单）:                   Asks（卖单）:
A: Buy  20 @ 10.90 (Id=1)      B: Sell 1  @ 11.00 (Id=5)  ← 减量保优先级
A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
C: Buy 100 @ 10.90 (Id=4)      B: Sell 5  @ 11.10 (Id=7)
A: Buy  5  @ 10.80 (Id=3)
B: Buy  20 @ 10.80 (Id=2)
```

> 关键观察：@10.90 价格档现在有 3 个买单，按 FIFO 排队：Id=1（最老）→ Id=8（次新）→ Id=4（最新，因为改了价格重新排队）。

---

**场景 1（撮合）：C 发送"卖 50 股 @ 10.90"的理解**

C 要**卖** 50 股，卖价 10.90。因为卖价 10.90 **等于**最高买价 10.90，所以这笔卖单是"主动卖单"（Aggressive Sell），会立即与买方订单撮合。

**撮合规则**：
- 始终从**最优价格**（最高买价/最低卖价）开始匹配
- 同价格内按 **FIFO 顺序**撮合
- 主动单数量不够 → 被动单部分成交；主动单数量有多 → 剩余停留为被动单

**逐笔匹配过程**：

```
C 要卖 50 股，卖价 10.90

Step 1: 找最高买价 → @10.90
        匹配 Id=1（FIFO 排头，20 股）
        → Id=1 全部成交（移除），C 还剩 30 股要卖
        成交量累计：20

Step 2: 仍在 @10.90 价格档
        匹配 Id=8（FIFO 第二位，10 股）
        → Id=8 全部成交（移除），C 还剩 20 股要卖
        成交量累计：30

Step 3: 仍在 @10.90 价格档
        匹配 Id=4（FIFO 第三位，100 股）
        → Id=4 部分成交 20 股（C 只需要 20 股了）
        → Id=4 剩余 80 股继续留在订单簿
        成交量累计：50 ✓ 卖完
```

**撮合结果**：

```
Bids（买单）:                   Asks（卖单）:
C: Buy  80 @ 10.90 (Id=4)      B: Sell 1  @ 11.00 (Id=5)
A: Buy  5  @ 10.80 (Id=3)      C: Sell 5  @ 11.00 (Id=6)
B: Buy  20 @ 10.80 (Id=2)      B: Sell 5  @ 11.10 (Id=7)

成交记录：C 以 10.90 的价格卖出了 50 股
（买方是 A 的 Id=1 和 Id=8，以及 C 自己的 Id=4——这里 C 的部分自己买自己卖）
```

---

**场景 2（撮合）：A 发送"买 10 股 @ 11.00"的理解**

A 要**买** 10 股，买价 11.00。因为买价 11.00 **等于**最低卖价 11.00，所以这笔买单是"主动买单"（Aggressive Buy），会立即与卖方订单撮合。

**逐笔匹配过程**：

```
A 要买 10 股，买价 11.00

Step 1: 找最低卖价 → @11.00
        匹配 Id=5（FIFO 排头，1 股）
        → Id=5 全部成交（移除），A 还剩 9 股要买
        成交量累计：1

Step 2: 仍在 @11.00 价格档
        匹配 Id=6（FIFO 第二位，5 股）
        → Id=6 全部成交（移除），A 还剩 4 股要买
        成交量累计：6

Step 3: @11.00 已经没有更多卖单了
        下一个卖价 @11.10 > 11.00，不匹配
        → A 剩余的 4 股无法成交，停留为被动买单
```

**撮合结果**：

```
Bids（买单）:                   Asks（卖单）:
A: Buy  4  @ 11.00 (新单)       B: Sell 5  @ 11.10 (Id=7)
C: Buy 80 @ 10.90 (Id=4)
A: Buy  5  @ 10.80 (Id=3)
B: Buy 20 @ 10.80 (Id=2)

成交记录：A 以 11.00 的价格买入了 6 股（B 的 1 股 + C 的 5 股）
剩余 4 股停留在 @11.00 成为买方被动单
```

> **核心要点回顾**：
> 1. 主动单的价格只要**等于或优于**被动单的最优价格就会触发撮合
> 2. 撮合时按**价格优先、时间优先（FIFO）**顺序匹配
> 3. 主动单不够吃时，被动单**部分成交**；主动单不够饱时，**剩余部分停留**为被动单
> 4. 订单簿的每一步变化都伴随着**优先级规则**（减量不变、增量/改价重新排队）

#### 5.2.5 订单修改规则

| 操作 | 对 FIFO 优先级的影响 |
|---|---|
| **减少数量** | **不改变**优先级，保持原位 |
| **增加数量** | **失去优先级**，排到同价格队尾 |
| **修改价格** | 等同于**撤单 + 新单**，重新排队 |
| **修改价格 + 数量** | 等同于**撤单 + 新单** |

#### 5.2.6 撮合引擎的线程模型与通信

```
订单网关响应 ──▶ ┌─────────────────┐ ──▶ 行情更新
  (SPSC)        │  Matching Engine │      (SPSC)
                │  (独立线程)      │
订单网关请求 ──▶ │                 │ ──▶ 客户端回报
  (SPSC)        └─────────────────┘      (SPSC)
```

| 设计要点 | 说明 |
|---|---|
| **独立线程** | 撮合引擎独占一个 CPU 核心，不被其他组件干扰 |
| **双向队列** | 订单网关 → 撮合引擎（请求），撮合引擎 → 订单网关（回应 + 成交通知） |
| **无锁 SPSC** | 使用第四章实现的 lock-free queue，避免内核态切换 |
| **内存池** | 订单对象从预分配内存池获取，避免 `new/delete` |

#### 5.2.7 订单簿的数据结构选择

| 需求 | 数据结构 | 原因 |
|---|---|---|
| 买卖盘排序 | 有序容器（按价格排序） | 撮合从最优价格开始 |
| 同价格 FIFO | 双向链表 | 高效的在头部/尾部插入删除 |
| 按价格查找 | HashMap（价格 → 价格档位） | O(1) 查找特定价格档位 |
| 按订单 ID 查找 | HashMap（订单 ID → 订单对象） | O(1) 查找/修改/删除特定订单 |

> 设计原则：**避免动态内存分配**。订单对象从内存池获取，节点来自预分配池，热路径上零 `new`/`delete`。

### 第 3 小节：行情发布器（Market Data Publisher）设计

#### 5.3.1 行情数据的两重角色

交易所向市场参与者发布两类信息：

| 类型 | 渠道 | 内容 | 受众 |
|---|---|---|---|
| **公共行情** | 行情发布器（UDP 组播） | 订单簿变更、成交信息 | **所有**市场参与者 |
| **私有通知** | 订单网关（TCP） | 订单状态更新、成交回报 | **只有**该订单的所属客户端 |

> 关键区别：公共行情隐藏了"哪个客户"的信息（公平性），私有通知只发给订单拥有者。

#### 5.3.2 行情消息类型

书中将市场数据消息分为以下几类：

| 消息类型 | 含义 | 典型字段 |
|---|---|---|
| **Order Add** | 新订单进入订单簿 | 品种 ID、订单 ID、价格、方向、数量、优先级 |
| **Order Modify** | 订单被修改（价格/数量变化） | 类似 Order Add，但含修改后状态 |
| **Order Delete** | 订单被移除（成交/撤单） | 品种 ID、订单 ID |
| **Trade** | 发生了撮合成交 | 品种 ID、主动方方向、成交价、成交量 |
| **Market State** | 市场状态变更 | 状态（Closed / PreOpen / Opening / Trading） |
| **Instrument Update** | 品种元数据变更 | 最小价格变动单位(tick size)、乘数等 |

> 行情协议的常见格式：FIX（TAG=VALUE 文本格式，灵活但冗余）、FAST（FIX 的压缩版）、EOBI/SBE（二进制打包结构，最快解码）。本书使用**自定义二进制打包协议**。

#### 5.3.3 增量流与快照流

这是行情设计中最重要的概念之一：

| 流类型 | 特点 | 用途 |
|---|---|---|
| **增量流（Incremental）** | 只推送订单簿的**变化**（新单/改单/撤单/成交） | 正常运行时维护订单簿，带宽低、延迟低 |
| **快照流（Snapshot）** | 推送整个订单簿的**完整快照** | 启动时初始化、丢包后恢复 |

**为什么需要两套流？**

UDP 组播虽然延迟低，但不保证可靠到达。如果客户端丢了一个增量包，订单簿就与实际状态不一致了。恢复流程：

```
1. 检测丢包（序列号不连续）
2. 清空本地订单簿
3. 订阅快照流，等待完整快照到达
4. 期间缓存在此之后的增量更新
5. 从快照重建完整订单簿 → 应用缓存的增量更新 → 同步完成
6. 退订快照流，只依赖增量流
```

#### 5.3.4 行情发布器的子组件

```
Market Data Publisher
├── Market Data Encoder（行情编码器）
│   ├── 从撮合引擎消费订单簿变更
│   ├── 转换为行情协议格式
│   ├── 发布到 UDP 增量组播流
│   └── 同时推送给 Snapshot Synthesizer
│
└── Snapshot Synthesizer（快照合成器）—— 独立线程
    ├── 消费编码后的增量更新
    ├── 合成完整订单簿快照
    ├── 附加快照序列号（上次增量流序列号）
    └── 周期性发布到 UDP 快照组播流
```

> 快照合成器是**独立线程**，不阻塞增量流的实时发布。它对延迟不敏感（本身就是延迟的、降采样的流）。

#### 5.3.5 为什么行情用 UDP 而不是 TCP？

| 考量 | UDP | TCP |
|---|---|---|
| 延迟 | 更低，无确认和重传 | 较高，需确认和重传 |
| 吞吐 | 更高，无 ACK 带宽开销 | 较低，有额外带宽开销 |
| 可靠性 | 不可靠，可能丢包 | 可靠，保证到达和顺序 |
| 扩展性 | 组播：一份数据所有订阅者同时收到 | 单播：每条连接独立发送 |
| 解决方案 | 快照流 + 序列号提供恢复机制 | 天然可靠 |

### 第 4 小节：订单网关（Order Gateway）设计

#### 5.4.1 订单网关的角色定位

订单网关是交易所和客户端之间的**双向通信桥梁**：

```
客户端 ←─ TCP ─→ 订单网关服务器 ←─ SPSC 队列 ─→ 撮合引擎
```

| 方向 | 内容 |
|---|---|
| 客户端 → 订单网关 | 新单、改单、撤单请求 |
| 订单网关 → 撮合引擎 | 翻译为内部格式的订单请求 |
| 撮合引擎 → 订单网关 | 订单处理结果、成交通知 |
| 订单网关 → 客户端 | 订单状态更新、成交回报 |

#### 5.4.2 订单网关的子组件

```
Order Gateway Server
├── TCP Connection Manager（连接管理器）
│   ├── 监听并接受客户端的 TCP 连接
│   ├── 管理活跃连接列表
│   ├── 检测断开并清理
│   └── 将撮合引擎的回应路由到正确的客户端连接
│
├── FIFO Sequencer（FIFO 排序器）
│   └── 确保多条客户端连接的请求按到达时间顺序转发
│
└── Protocol Encoder/Decoder（协议编解码器）
    ├── 将客户端请求（交易所协议）解码为撮合引擎内部格式
    └── 将撮合引擎回应编码为交易所协议格式
```

#### 5.4.3 为什么订单网关用 TCP 而不是 UDP？

| 原因 | 说明 |
|---|---|
| **可靠性** | 订单一旦发出就不能丢失，必须保证送达 |
| **有序性** | 订单的顺序很重要（先发先处理），TCP 天然有序 |
| **双向通信** | 客户端同时发送请求和接收回应 |
| **连接状态** | 需要明确知道客户端是否在线 |

#### 5.4.4 FIFO Sequencer 的作用

公平性是交易所的核心原则。如果两个客户端同时发送订单，先到达交易所网关的应该先被处理：

```
Client A 连接 ──┐
                 ├── FIFO Sequencer ──▶ 撮合引擎（按到达时间排序）
Client B 连接 ──┘
```

这确保即使不同 TCP 连接的内核 buffer 处理有微小差异，最终转发给撮合引擎的顺序仍然是**到达交易所硬件的实际顺序**。

#### 5.4.5 生产环境中的附加功能（本书简化处理）

| 功能 | 说明 |
|---|---|
| 客户端认证（Logon） | 身份验证、密码检查 |
| 心跳（Heartbeat） | 检测连接存活，低活动期保持连接 |
| 应用层序列号 | 额外的可靠性保障，与 TCP 互补 |
| 负载均衡 | 多连接分散到不同订单网关实例 |

│                │                                  │
└──────────────────────────────────────────────────┘

#### 5.5.2 行情消费器（Market Data Consumer）

| 职责 | 说明 |
|---|---|
| **UDP 订阅** | 加入交易所行情组播地址 |
| **协议解码** | 将交易所行情格式解码为内部标准化格式 |
| **快照同步** | 启动/丢包时执行增量+快照同步流程 |
| **跨交易所标准化** | 不同交易所的格式统一为内部标准格式 |

**快照同步流程**：

```
Step 1: 清空订单簿，订阅快照流
Step 2: 继续收取增量流数据并缓存
Step 3: 收到完整快照 → 重建订单簿
Step 4: 将缓存的增量更新（从 snapshot 序列号之后开始）应用到订单簿
Step 5: 同步完成，退订快照流
```

#### 5.5.3 客户端订单簿

客户端也需要维护一份订单簿，但与交易所撮合引擎的订单簿有所不同：

| 差异点 | 交易所订单簿 | 客户端订单簿 |
|---|---|---|
| 知道订单所属方 | 知道每笔订单属于哪个客户 | 不知道（公有行情隐藏了客户 ID） |
| 实时性 | 实时 | 略微延迟（网络传输 + 解码） |
| 撮合功能 | 需要撮合 | 不需要撮合，只需更新 |
| 自有订单跟踪 | 不需要 | 通常需要知道自己的订单在 FIFO 队列中的位置 |

#### 5.5.4 Feature Engine（特征引擎）

特征引擎基于订单簿数据生成交易信号：

```
订单簿 ──▶ Feature Engine ──▶ 特征值 ──▶ 交易策略
              │
              ├── 市场公允价格（基于 TOB 价格和数量加权）
              ├── 买卖压力指标
              ├── 成交量异常检测
              └── 市场微观结构信号
```

> 本书只实现**最简特征引擎**：计算 TOB 加权公允价格和主动单相对 TOB 数量的比率。生产环境中特征引擎可以非常复杂，包含统计模型、机器学习等。

**逐概念解释**：

**（1）TOB（Top of Book，最优报价）**

TOB 是订单簿的"顶部"，即**最高的买价**和**最低的卖价**：

```
Bids:                          Asks:
@10.90: 20+10+100 股           @11.00: 1+5 股
@10.80: 5+20 股                @11.10: 5 股
      ↑ 最高买价 = 10.90             ↑ 最低卖价 = 11.00
      └─── Best Bid ────┘     └─── Best Ask/Offer ────┘
      └────────────── TOB（最优报价） ──────────────┘
```

- Best Bid（最优买价）：10.90，数量 = 20+10+100 = 130 股
- Best Ask（最优卖价）：11.00，数量 = 1+5 = 6 股
- Mid-price（中间价）：(10.90 + 11.00) / 2 = 10.95

**（2）TOB 加权公允价格（TOB-Weighted Fair Price）**

简单取中间价（mid-price）有一个问题：它**忽略了买卖双方的流动性分布**。同样是中间价 10.95，如果买单有 130 股而卖单只有 6 股，说明市场在买方有更厚的支撑，公允价格应该**偏向买方**。

加权公式：

```
                     BidPrice × AskQty + AskPrice × BidQty
FairPrice = ──────────────────────────────────────────────────
                          BidQty + AskQty
```

代入上面的数字：

```
             10.90 × 6 + 11.00 × 130        65.4 + 1430          1495.4
FairPrice = ────────────────────────── = ────────────────── = ──────────── ≈ 10.99
                    6 + 130                    136                136
```

对比：

| 价格 | 公式 | 值 | 含义 |
|---|---|---|---|
| Mid-price | `(Bid + Ask) / 2` | 10.95 | 不考虑流动性分布 |
| TOB 加权公允价 | `(Bid×AskQty + Ask×BidQty) / (BidQty + AskQty)` | 10.99 | 偏向流动性更厚的一方 |

因为买单数量（130）远大于卖单数量（6），加权价格从 10.95**上移**到 10.99，更靠近买方——反映市场"买压大于卖压"。

**（3）主动单（Aggressive Order）**

回顾第 2 小节的术语：

| 类型 | 行为 | 例子 |
|---|---|---|
| **被动单（Passive）** | 挂在订单簿里等待成交 | Buy @ 10.90 → 在 Bid 侧等待 |
| **主动单（Aggressive）** | 以对侧价格立即成交 | Sell @ 10.90 → 直接吃掉 Bid 侧的被动买单 |

主动单的特征：它的价格**等于或优于**对侧的最优价格，因此一进入市场就立即撮合。

**（4）TOB 数量**

就是最优报价档位的总数量：

- TOB Bid Qty = Best Bid 价位的所有买单数量之和（上例中：130 股）
- TOB Ask Qty = Best Ask 价位的所有卖单数量之和（上例中：6 股）

**（5）"主动单相对 TOB 数量的比率"的含义**

```
ratio = 主动单数量 / 同一侧 TOB 数量
```

这个比率回答了一个问题：**"这笔主动交易吃掉了对应侧顶部流动性的多少？"**

举例（同一订单簿状态）：

- 一笔主动卖单 Sell 50 @ 10.90，对手侧是 Bid（TOB Bid Qty = 130）
  - ratio = 50 / 130 ≈ 0.38 → 吃掉了买方最优价格的 38% 流动性
  - 如果 TOB Bid Qty 只有 20，ratio = 50/20 = 2.5 → 要吃穿好几档价格！

- 一笔主动买单 Buy 4 @ 11.00，对手侧是 Ask（TOB Ask Qty = 6）
  - ratio = 4 / 6 ≈ 0.67 → 吃掉了卖方最优价格的 67% 流动性

**这个比率有什么用？**

| ratio 大小 | 含义 | 策略信号 |
|---|---|---|
| ratio ≪ 1（远小于 1） | 主动单远小于 TOB 流动性，无法推动价格 | 正常交易，市场价格稳定 |
| ratio ≈ 1 | 主动单接近吃光最优价格档位 | 可能导致价格变动（最优价被吃完，次优价上升为最优价） |
| ratio > 1 | 主动单超过最优价格流动性，需要穿透多档 | 价格可能剧烈跳动，市场压力信号 |

> **一句话总结**：
> - **TOB 加权公允价格**：用买卖数量做权重算出的"公平价"，比简单中间价更能反映市场的真实供需偏向。
> - **主动单相对 TOB 数量的比率**：衡量一笔交易的"冲击力"——吃掉了多少顶层流动性，ratio 越大对价格的推动力越强。
> - 两个特征组合起来，策略就能判断：当前市场"偏买还是偏卖"（公允价），以及进来的交易"有多大冲击"（比率）。

#### 5.5.5 PositionKeeper（仓位跟踪器）

| 职责 | 说明 |
|---|---|
| 处理成交记录 | 根据成交更新仓位 |
| 计算持仓 | 多空方向净持仓 |
| 计算 PnL | 已实现盈亏 + 未实现盈亏 |
| 持仓成本 | 加权平均成交价 |

#### 5.5.6 Order Manager（订单管理器）

Order Manager 是整个客户端策略框架中最复杂的组件之一，负责管理策略所有活跃订单的生命周期。

**核心职责**：

| 职责 | 说明 |
|---|---|
| 发送订单 | 将策略的订单请求编码并发送 |
| 管理状态 | 跟踪每个订单的状态（发送中/活跃/部分成交/已成交/已取消） |
| 处理 in-flight 冲突 | 撤单请求正在路上，但订单已被撮合 |
| 处理成交 | 部分/全部成交的状态更新 |
| 去重和序列号 | 应用层保证不重不漏 |

**In-Flight 冲突示例**：

```
时间线：
T1: 客户端发送 Cancel OrderId=5 的请求
T2: 同时，交易所匹配引擎收到了一个 Aggressive Buy，把 OrderId=5 撮合了
T3: Cancel 请求到达交易所 ──▶ OrderId=5 已不存在 ──▶ Cancel Reject

Order Manager 需要正确处理：
  - 收到 T2 的成交通知（来自行情或订单网关）
  - 收到 T3 的撤单拒绝
  - 知道这个订单已经不存在了，不能重复发出请求
```

#### 5.5.7 Risk Manager（风险管理器）

| 风险类别 | 具体指标 | 说明 |
|---|---|---|
| **订单量** | 单笔订单最大数量 | 防止"胖手指"错误 |
| **持仓** | 当前净持仓 | 直接决定市场风险暴露 |
| **最坏情况持仓** | 含所有活跃买单的潜在持仓 | 极端情况下的风险 |
| **盈亏** | 已实现 + 未实现盈亏 | 跟踪实际损失 |
| **交易量** | 累计交易量上限 | 防止算法失控 |
| **频率** | 订单/成交/亏损的滑动窗口统计 | 防止异常交易行为 |

> 实际系统中有**多层风控**：策略层、订单网关客户端层、清算经纪商后台层。本书实现策略层的基础风控。

#### 5.5.8 两种核心交易策略

| 策略类型 | 角色 | 订单类型 | 利润来源 |
|---|---|---|---|
| **Market Maker（做市商）** | 流动性提供者 | 双边挂单（同时挂买单和卖单） | 买卖价差 |
| **Liquidity Taker（流动性提取者）** | 流动性消费者 | 主动吃单 | 预测价格方向 |

**Market Maker**：
- 在最优买价和卖价附近各挂一个单
- 赚取 bid-ask spread
- 风险：逆向选择（价格朝不利方向移动时没来得及撤单）

**Liquidity Taker**：
- 基于信号/预测决定买卖方向
- 主动以对侧价格成交
- 风险：信号质量、延迟

### 必做

1. **画出系统拓扑图**
   - 手绘或用工具画出交易所 + 客户端的完整拓扑图。
   - 标注每个组件间的通信方式和数据流向（无锁队列 / UDP / TCP）。
   - 思考：为什么撮合引擎、行情发布器、订单网关要设计为独立线程？
   <details>
   <summary><b>思考答案</b></summary>

   这个设计的根本原因在于：**这三个组件有不同的延迟约束和阻塞风险源，放在同一个线程里会导致互相拖累**。

   具体分析每个组件的"为什么不能与别的东西共享线程"：

   | 组件 | 如果与其他组件共享线程会发生什么 | 所以必须独立 |
   |---|---|---|
   | **撮合引擎** | 撮合是 CPU 密集型操作。行情高峰时，一个主动大单可能触发几十笔连续撮合（遍历买卖盘、更新订单簿）。如果同线程还要处理 TCP 连接的 I/O 事件，撮合延迟会因 I/O 等待而大幅抖动。 | 撮合引擎需要独占一个 CPU 核心，不做任何网络 I/O，专心匹配订单。 |
   | **行情发布器** | UDP 组播发送可能有瞬时瓶颈（网卡队列满 → 系统调用阻塞）。如果和撮合引擎共用线程，一次 UDP 发送卡顿就会直接推高撮合延迟。反过来，如果撮合卡住，行情也发不出去。 | 行情发布器独立运行，撮合慢不影响行情发送，行情发送慢也不耽误撮合。 |
   | **订单网关** | TCP `accept()`、`recv()`、`send()` 都会因客户端行为而阻塞（慢客户端、断连重试、TCP 拥塞控制）。如果把这些 I/O 操作放在撮合线程里，一个慢客户端就能拖慢整个交易所的撮合速度。 | 订单网关独立处理所有 TCP 连接管理，通过 SPSC 队列与撮合引擎异步通信，实现连接管理与撮合逻辑的彻底隔离。 |

   除了"负面隔离"之外，独立线程还有正向收益：

   1. **并行吞吐**：三个组件可以同时在不同 CPU 核心上运行。行情爆发时，撮合引擎忙着匹配、行情发布器忙着编码发送、订单网关忙着收发 TCP——三者并行，吞吐量成倍提高。
   2. **独立的 CPU 绑定策略**：撮合引擎绑定到隔离核心（`isolcpus`），追求最低延迟抖动；行情发布器和订单网关可以绑定到不同核心，根据负载分别调优。
   3. **独立停启和升级**：可以单独重启订单网关（如更换协议编解码器）而不中断撮合引擎和行情发布。

   书中明确说："the matching engine, the market data publisher, and the order gateway server will be independent threads. This is intentional so that each one of these components can operate independently, and during periods of bursts in market activity, the entire system can achieve maximum throughput."

   通信代价通过**无锁 SPSC 队列**（第四章产物）来承担——线程间的数据传递只有原子变量的读/写开销，无需系统调用、不进入内核态、不阻塞。
   </details>

   **操作 1：A 发送新买单 Buy 10 @ 10.90**

   → 新增 OrderId=8。10.90 = 最高买价，与现有 Id=1 同价。
   → FIFO 规则：Id=8 排在 Id=1 后面。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1) ←排头 B: Sell 10 @ 11.00 (Id=5)
   A: Buy  10 @ 10.90 (Id=8) ←新增 C: Sell 5  @ 11.00 (Id=6)
   A: Buy  10 @ 10.80 (Id=2)      B: Sell 5  @ 11.10 (Id=7)
   B: Buy  5  @ 10.80 (Id=3)
   C: Buy 100 @ 10.70 (Id=4)
   ```

   ---

   **操作 2：B 发送新卖单 Sell 10 @ 11.20**

   → 新增 OrderId=9。11.20 > 最低卖价 11.00，排在卖单队尾。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1)      B: Sell 10 @ 11.00 (Id=5)
   A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
   A: Buy  10 @ 10.80 (Id=2)      B: Sell 5  @ 11.10 (Id=7)
   B: Buy  5  @ 10.80 (Id=3)      B: Sell 10 @ 11.20 (Id=9) ←新增队尾
   C: Buy 100 @ 10.70 (Id=4)
   ```

   ---

   **操作 3：A 将 OrderId=2 的数量从 10 改为 20（增加数量）**

   → 数量增加了。FIFO 规则：**增加数量 → 失去优先级，排到同价队尾**。
   → Id=2 原来排在 @10.80 的第一位（在 Id=3 前面），现在被移到 @10.80 的最后一位（Id=3 后面）。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1)      B: Sell 10 @ 11.00 (Id=5)
   A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
   B: Buy  5  @ 10.80 (Id=3) ←升头 B: Sell 5  @ 11.10 (Id=7)
   A: Buy  20 @ 10.80 (Id=2) ←移后 B: Sell 10 @ 11.20 (Id=9)
   C: Buy 100 @ 10.70 (Id=4)
   ```

   关键理解：Id=3 原来在 Id=2 后面，现在 Id=2 被"推"到后面去了。Id=3 从排第二变成了排第一。

   ---

   **操作 4：B 将 OrderId=5 的数量从 10 改为 1（减少数量）**

   → 数量减少了。FIFO 规则：**减少数量 → 保留优先级，位置不动**。
   → Id=5 仍然是 @11.00 的排头。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1)      B: Sell 1  @ 11.00 (Id=5) ←只改了数量，位置不变
   A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
   B: Buy  5  @ 10.80 (Id=3)      B: Sell 5  @ 11.10 (Id=7)
   A: Buy  20 @ 10.80 (Id=2)      B: Sell 10 @ 11.20 (Id=9)
   C: Buy 100 @ 10.70 (Id=4)
   ```

   关键理解：减量 → 不排队。原因是"少卖一点"并不伤害其他排队者，"多买一点"才会。

   ---

   **操作 5：C 将 OrderId=4 的价格从 10.70 改为 10.90（修改价格）**

   → FIFO 规则：**修改价格 → 等同于撤单 + 新单，完全重新排队**。
   → Id=4 从 @10.70 移除，作为新订单插入 @10.90 队尾。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1)      B: Sell 1  @ 11.00 (Id=5)
   A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
   C: Buy 100 @ 10.90 (Id=4) ←改价 B: Sell 5  @ 11.10 (Id=7)
   B: Buy  5  @ 10.80 (Id=3)      B: Sell 10 @ 11.20 (Id=9)
   A: Buy  20 @ 10.80 (Id=2)
   ```

   关键理解：@10.70 档位消失了（那个档位只有 Id=4 一个订单），@10.90 档位现在有三个订单：Id=1 → Id=8 → Id=4。

   ---

   **操作 6：B 撤销 OrderId=9（撤单）**

   → Id=9 从卖单中直接移除。

   ```
   Bids:                           Asks:
   A: Buy  20 @ 10.90 (Id=1)      B: Sell 1  @ 11.00 (Id=5)
   A: Buy  10 @ 10.90 (Id=8)      C: Sell 5  @ 11.00 (Id=6)
   C: Buy 100 @ 10.90 (Id=4)      B: Sell 5  @ 11.10 (Id=7)
   B: Buy  5  @ 10.80 (Id=3)
   A: Buy  20 @ 10.80 (Id=2)
   ```

   此时 **撮合前状态** 确定。最优买价 = 10.90，最优卖价 = 11.00。10.90 < 11.00，无交叉，无撮合。

   ---

   **操作 7（撮合场景 1）：C 发送 Sell 50 @ 10.90**

   → 主动卖单，卖价 10.90 = 最高买价 → 触发撮合。
   → 逐笔匹配：找 @10.90 的买单，FIFO 顺序为 Id=1 → Id=8 → Id=4。

   ```
   C 要卖 50 股，从最优买价开始向下吃：

   Step A: @10.90, Id=1（FIFO 排头，20 股）
           → 全部成交，Id=1 被移除。C 剩余 30 股。
   Step B: @10.90, Id=8（FIFO 次位，10 股）
           → 全部成交，Id=8 被移除。C 剩余 20 股。
   Step C: @10.90, Id=4（FIFO 第三位，100 股）
           → 部分成交 20 股，剩余 80 股。C 卖完 ✓
   ```

   撮合后：
   ```
   Bids:                           Asks:
   C: Buy  80 @ 10.90 (Id=4)      B: Sell 1  @ 11.00 (Id=5)
   B: Buy  5  @ 10.80 (Id=3)      C: Sell 5  @ 11.00 (Id=6)
   A: Buy  20 @ 10.80 (Id=2)      B: Sell 5  @ 11.10 (Id=7)

   成交记录：C 以 @10.90 卖出 50 股
   ```

   ---

   **操作 8（撮合场景 2）：A 发送 Buy 10 @ 11.00**

   → 主动买单，买价 11.00 = 最低卖价 → 触发撮合。
   → 逐笔匹配：找 @11.00 的卖单，FIFO 顺序为 Id=5 → Id=6。

   ```
   A 要买 10 股，从最低卖价开始向上吃：

   Step A: @11.00, Id=5（FIFO 排头，1 股）
           → 全部成交，Id=5 被移除。A 剩余 9 股。
   Step B: @11.00, Id=6（FIFO 次位，5 股）
           → 全部成交，Id=6 被移除。A 剩余 4 股。
   Step C: @11.00 已空。下一个卖价 @11.10 > 11.00 → 不匹配。
           → A 剩余 4 股无法成交，作为被动买单停留。
   ```

   撮合后：
   ```
   Bids:                           Asks:
   A: Buy  4  @ 11.00 (新单Id=10)  B: Sell 5  @ 11.10 (Id=7)
   C: Buy  80 @ 10.90 (Id=4)
   B: Buy  5  @ 10.80 (Id=3)
   A: Buy  20 @ 10.80 (Id=2)

   成交记录：A 以 @11.00 买入 6 股，剩余 4 股被动挂单
   ```

   ---

   **（4）FIFO 优先级规则总结**

   | 操作 | 优先级变化 | 背后的逻辑 |
   |---|---|---|
   | 新单（New） | 排在**同价队尾** | 后来者排在已经等了的人后面 |
   | 减少数量（Modify Qty ↓） | **不变** | 少卖/少买不影响队列中的其他人 |
   | 增加数量（Modify Qty ↑） | 失去优先级，**重新排到队尾** | 想多买 → 相当于新增了部分需求，应该重新排队 |
   | 修改价格（Modify Price） | **优先权重置**（=撤单+新单） | 价格变了意味着意愿变了，不应该还能享受老位置的优先权 |
   | 撤单（Cancel） | **从列表移除** | 不玩了就腾出位置 |

   </details>

3. **设计增量 + 快照同步流程**
   - 用自己的话描述快照同步的完整流程。
   - 思考：为什么快照需要包含"最后应用的增量序列号"？
   - 如果客户端在同步期间又丢了一个包，怎么处理？
   <details>
   <summary><b>思考答案</b></summary>

   **（1）为什么快照需要包含"最后应用的增量序列号"？**

   假设增量流有以下消息：
   ```
   增量序列号:  100    101    102    103    104    105
   内容:       [Add]  [Mod]  [Add]  [Del]  [Add]  [Mod]
                                          ↑
                              快照合成时使用的最后一个增量号 = 103
   ```

   快照发布时会附上 `last_inc_seq_num = 103`。客户端收到快照后：
   - 从快照重建订单簿（这个状态对应到增量号 103）
   - 从增量号 104 开始应用缓存的增量更新
   - 如果不带这个序列号，客户端不知道"快照对应到哪一条增量"，无法精确对齐

   **（2）同步期间又丢了一个包怎么办？**

   这是**双层兜底**的思路：
   1. 重新开始同步：清空订单簿、清空缓存 → 重新订阅快照流 → 等待下一个快照 → 重新应用增量。
   2. 如果连续失败，可能网络有问题，触发告警、切到备用网络路径。
   3. 在等待同步完成的期间，策略暂停交易（或只平仓不开仓），避免基于错误订单簿做决策。

   快照流每几秒发布一次，所以最坏情况就是多等几秒。
   </details>

4. **分析订单簿数据结构需求**
   - 列出撮合引擎订单簿所有的操作需求（添加、删除、修改、按价格查找、按 ID 查找、匹配）。
   - 为每个操作选择合适的数据结构，说明选择理由。
   - 思考：为什么使用内存池比直接 `new/delete` 更好？
   <details>
   <summary><b>思考答案</b></summary>

   这个问题要从**撮合引擎订单簿的运行模式**来理解。

   撮合引擎的订单簿（第 6 章将实现 `MEOrderBook`）需要频繁创建和销毁两种对象：

   - **`MEOrder`**（订单对象）：每次客户端提交新单、或撤单后再发新单，都需要创建一个 `MEOrder` 塞入价格档位的链表。
   - **`MEOrdersAtPrice`**（价格档位节点）：当一个价格档位首次出现订单时，需要在 HashMap 中插入一个新的价格档位节点；当该档位的最后一个订单被撤/成交后，节点要被删除。

   在行情高峰期，每秒可能有**上万次订单创建和销毁**。

   如果用 `new/delete`：

   | 问题 | 具体表现 |
   |---|---|
   | **系统调用** | 默认分配器（glibc malloc）在需要新内存时调用 `brk()` 或 `mmap()`，这是内核态操作。一次 `new` 可能耗时从几百纳秒到几百微秒不等，完全不可预测。 |
   | **锁竞争** | 默认分配器有全局锁（arena lock）。多线程同时分配时，线程 A 的分配被线程 B 的锁阻塞——撮合引擎所在的线程也可能被其他无关线程的分配行为间接阻塞。 |
   | **内存碎片** | 订单对象大小固定，但 `new/delete` 的分配/释放交错进行，时间久了堆碎片化。分配器需要花更长时间在碎片中搜索合适的空闲块——延迟随时间增长。 |
   | **缓存失效** | `new` 返回的地址完全随机分布，相邻订单可能在物理上相距很远。遍历订单簿时 cache miss 严重。 |

   内存池（第 4 章已实现的 `FixedMemoryPool`）如何解决：

   | 内存池特性 | 对应解决 |
   |---|---|
   | 预分配一大块连续内存 | 不需要系统调用，分配只是从 free_list 弹出一个指针 |
   | 单线程独立池（thread-local） | 完全无锁 |
   | 固定大小的 block | 不会产生碎片，每次分配耗时恒定 |
   | 所有 block 在同一块连续内存中 | 相邻订单的缓存命中率高 |

   对于撮合引擎来说，**确定性延迟**是最关键的——你不能让一次匹配操作因为 `new` 触发了 `mmap` 而突然多花 50 微秒。内存池把这个不可预测的来源彻底消除了。
   </details>

5. **调研真实交易所协议**
   - 了解 Nasdaq ITCH/OUCH 或 CME iLink/MDP 的基本格式。
   - 对比教材的简化协议与真实协议的差异。
   - 思考：为什么二进制协议比文本协议更适合低延迟？
   <details>
   <summary><b>思考答案</b></summary>

   这个问题从**交易所行情处理的实时性**来理解最清楚。

   行情流的特点：每秒可能有几万条消息（新单、改单、撤单、成交），每条消息都必须尽快解码以更新客户端订单簿。解码延迟直接决定策略决策的及时性。

   **文本协议（如 FIX）的解析开销**：

   以 FIX 为例，一条行情消息是这样组织的：
   ```
   35=X|268=1|279=0|269=0|48=68475|270=175.16|271=1000|...
   ```

   解码这条消息需要：
   1. 按分隔符 `|` 切分 TAG=VALUE 对
   2. 对每个 TAG，做字符串比较来确定它是哪个字段（`"268"` → NoMDEntries）
   3. 对每个 VALUE，做字符串到数字的转换（`"175.16"` → double, `"1000"` → int）
   4. 每个步骤都涉及内存遍历、字符比较、函数调用——CPU 密集且分支不可预测

   **二进制协议（如 SBE / 本书自定义协议）的零开销解码**：

   ```
   二进制字节流: [0x04][0x00][0x00][0x00]...
   ↓ reinterpret_cast
   结构体字段:    msg_type = 4   (直接读取)
   ```

   二进制消息的每个字段在字节流中有固定偏移。你只需要把接收 buffer 的指针 `reinterpret_cast` 成协议结构体指针，然后直接访问字段——**零解析开销**。不需要字符串分割、不需要 TAG 查表、不需要 `atoi`/`atof`。

   | 对比维度 | 文本协议（FIX） | 二进制协议（SBE / 本书协议） |
   |---|---|---|
   | 解码方式 | 字符串分割 + TAG 匹配 + 类型转换 | `reinterpret_cast` + 直接字段访问 |
   | CPU 开销 | 高（字符遍历、分支密集） | 极低（只是指针转换和内存读取） |
   | 内存分配 | 通常需要创建 string 对象 | 无分配，直接在 receive buffer 上操作 |
   | 消息体积 | 大（TAG=VALUE 文本膨胀 2-5×） | 小（固定长度字段） |
   | 延迟稳定性 | 因字符串长度不同而抖动 | 固定长度，延迟确定 |

   本书行情协议（第 7 章实现）使用 **packed binary structure**：`#pragma pack(push, 1)` 确保结构体按字节紧密排列，网络收到的字节流可以直接映射到 C++ 结构体上。解码"就是"访存。

   代价：二进制协议不可读，调试时需要专门的解析工具；修改字段顺序或增加字段时必须小心维护兼容性。
   </details>

6. **设计更完善的 FIFO 规则**
   - 调研 Pro Rata 匹配算法。
   - 思考：如果交易所支持多种撮合算法，订单簿数据结构需要怎样改动？
   <details>
   <summary><b>思考答案</b></summary>

   **先回顾当前（仅 FIFO）的订单簿数据结构**（第 6 章实现）：

   ```
   MEOrderBook
   ├── bids_: 按价格排序的 bid 价格档位（HashMap<Price, MEOrdersAtPrice*>）
   ├── asks_: 按价格排序的 ask 价格档位
   │
   └── MEOrdersAtPrice（每个价格档位）
       ├── price_: 该档位价格
       ├── side_: 买/卖
       ├── first_order_: 指向第一个 MEOrder（FIFO 排头）
       └── last_order_: 指向最后一个 MEOrder（FIFO 队尾）
           │
           └── MEOrder（每个订单，双向链表节点）
               ├── prev_order_ / next_order_: 同档位链表指针
               ├── order_id_ / client_id_ / price_ / qty_ / side_
               └── priority_: 在该档位中的 FIFO 顺序
   ```

   **关键观察**：当前设计中，FIFO 的"先到先得"语义是**隐含的**——它由 `MEOrder` 在双向链表中的位置决定（排头 = 最高优先级）。如果只支持 FIFO，这不是问题。但一旦引入 Pro Rata，你就需要**显式处理优先级和分配比例**。

   **需要使用多种撮合算法的改动**：

   1. **`MEOrder` 需要新增字段**：
      - 当前已经有 `priority_` 字段（FIFO 序号），这对 FIFO 够用。
      - 对于 Pro Rata，还需要新增 `displayed_qty_`（显示数量）和 `hidden_qty_`（隐藏数量）——Pro Rata 可能只按显示数量分配，冰山订单的隐藏部分不参与比例计算。
      - 如果是 Time-Pro Rata 混合，还需要记录订单的精确到达时间戳（`arrival_time_`），而非仅靠链表位置推断。

   2. **`MEOrdersAtPrice` 需要解耦"排序"和"撮合"**：
      - 当前设计隐式假设"排头就是下一个要撮合的订单"。
      - 改为两种职责分离：
        ```
        MEOrdersAtPrice {
            // 数据：订单集合（双链表仍可保留，用于遍历和删除）
            MEOrder* first_order_;
            MEOrder* last_order_;

            // 算法：如何在这一档内分配
            MatchingAlgorithm* algo_;  // FIFO / ProRata / TimeProRata
        }
        ```
      - `MatchingAlgorithm` 提供接口：`match_aggressive(MatchingContext& ctx)`，FIFO 实现按链表顺序撮合，Pro Rata 实现按数量比例遍历整条链表。

   3. **HashMap 和价格排序结构不变**：
      - `bids_` / `asks_` 的 HashMap<Price, MEOrdersAtPrice*> 保持不变——无论用什么撮合算法，按价格先到先匹配的规则不变。
      - 价格的排序（bid 从高到低，ask 从低到高）也不受影响——这属于**跨档位**的匹配规则，与**档位内**的分配算法是正交的。

   4. **`MEOrderBook` 需要按品种做算法选择**：
      - 实际交易所不同品种可能用不同算法（股票 FIFO、期货 Pro Rata）。
      - 订单簿初始化时需要传入品种的算法类型：
        ```
        MEOrderBook::MEOrderBook(TickerId tid, MatchingAlgoType algo)
        ```

   **本质上的改动**：引入一个**策略模式**，把"在同一价格档内如何分配成交量"的逻辑从 `MEOrdersAtPrice` 的数据结构中抽出来，做成可插拔的——数据结构本身只需暴露足够的信息（订单列表、每个订单的数量和优先级），让算法去做决策。
   </details>

**Q1：为什么行情发布器用 UDP 而订单网关用 TCP？这个选择是绝对的吗？**

<details>
<summary><b>点击展开答案</b></summary>

**（1）为什么行情用 UDP？—— 逐条对应"如果不用 UDP 会怎样"**

| 如果改用 TCP | 具体后果 |
|---|---|
| 一个发布器要给 100 个客户端发数据 → 需要维护 100 条 TCP 连接 | 每个连接独立发送相同数据，发布器的网卡带宽和 CPU 被 100× 放大。行情高峰时发不过来，消息排队，延迟飙升。 |
| TCP 的可靠性机制（ACK + 重传）在流媒体场景下反而有害 | 如果某个客户端的 ACK 慢了（网络抖动），TCP 拥塞窗口缩小，发布器整个发送节奏被打乱——一个慢客户端拖慢所有客户端。 |
| TCP 是单播（一对一） | 一条消息要发 100 次。UDP 组播是一对多，消息发一次，交换机复制给所有订阅者——带宽省 100 倍、延迟低一个数量级。 |

关键观点：**行情不是不能丢，而是丢掉一条不影响全局**——因为下一条增量更新会覆盖旧状态，而且快照流兜底。

**（2）为什么订单网关用 TCP？—— 逐条对应"如果改用 UDP 会怎样"**

| 如果改用 UDP | 具体后果 |
|---|---|
| UDP 不保证到达 → 客户端无法确认订单是否真的发到了交易所 | 一笔大单发出去了，不知道成没成。这在金融上不可接受。 |
| UDP 不保证顺序 → 客户端发了"新单→改单→撤单"，到达顺序变成"改单→撤单→新单" | 交易所收到的是一个已撤销的订单先发撤销请求、然后新单才到——全部乱序，逻辑崩溃。 |
| UDP 无连接状态 → 交易所不知道客户端是否还"在线" | TCP 断开连接是一个明确的信号（客户端掉线 → 可以触发紧急撤单）；UDP 没有这个信号，你需要自己实现心跳和超时。 |

关键观点：**订单关乎金钱和法律责任**，必须在"到达 → 确认 → 有序"这个链条上零容忍错误。TCP 的重量级可靠性机制恰好匹配这个需求。

**（3）这个选择是否绝对？—— 具体反例**

| 反例 | 说明 |
|---|---|
| **行情也可以用 TCP** | 连接数少的场景（如只有几家做市商的暗池）用 TCP 完全可行，反而更简单——不需要快照流。 |
| **订单网关也可以用 UDP** | 某些 HFT 专用连接上，客户端和交易所之间只有一根直连光纤，丢包率极低。此时可以在 UDP 上自建轻量可靠性层（应用层序列号 + 选择性重传 + 超时重发），避免 TCP 的拥塞控制引入抖动。这种方案比裸 TCP 的尾部延迟更低。 |
| **混合：行情增量用 UDP，快照用 TCP** | 一些交易所将快照流从 UDP 改为 TCP（因为同步时丢快照包的处理太麻烦），增量流继续用 UDP。本质上是一种折中。 |

> **结论**：UDP/行情 + TCP/订单是**当前主流的最优解**，但不是唯一解。选择取决于：参与者数量、网络质量、带宽预算、以及你愿意在应用层写多少可靠性代码。
</details>

**Q2：如果客户端同时依赖行情数据和订单网关回报来更新自己的订单状态，两个源可能不一致怎么办？**

<details>
<summary><b>点击展开答案</b></summary>

这是**Order Manager（订单管理器）**需要解决的核心问题之一。我们来分析"不一致"具体指什么场景，以及 Order Manager 如何设计来处理它。

**（1）不一致的三种具体场景**

| 场景 | 行情说了什么 | 订单网关说了什么 | 实际发生了什么 |
|---|---|---|---|
| **场景 A：时序分歧** | 一笔 Trade @11.00 Qty=6（没有客户信息），比 TCP 快 200μs 到达 | 200μs 后才收到"你的 OrderId=5 被全部成交" | 自己的卖单被撮合了。行情和回报信息一致，但到达时间差 200μs |
| **场景 B：丢包导致信息缺失** | 行情丢了一个 OrderDelete 包 → 你的订单簿上 OrderId=5 还在 | 订单网关发来了"OrderId=5 成交" | 你已经不知道 OrderId=5 还在不在——两条源都是真的，但你丢了一条 |
| **场景 C：真正的冲突（in-flight）** | 行情没有你的订单信息 | 订单网关收到你的撤单请求，但返回"撤单被拒——订单已成交" | 你发撤单的同时，一个主动单匹配了你的订单。两个事件在交易所几乎同时发生 |

**（2）为什么两条源会不一致？—— 交易所内部的物理路径差异**

```
撮合引擎完成匹配
    │
    ├──▶ 发送给行情发布器（SPSC 队列 → 编码 → UDP 发送）
    │              │
    │              └── 到达客户端（UDP 路径）
    │
    └──▶ 发送给订单网关（SPSC 队列 → 编码 → TCP 发送）
                   │
                   └── 到达客户端（TCP 路径）
```

两条路径的延迟差异来自：不同的 SPSC 消费速率、不同的编码时间、不同的网络协议栈（UDP 直发 vs TCP 需 ACK）。在 HFT 级别，差异可达几十到几百微秒。

**（3）Order Manager 的设计方案**

在客户端的架构中，Order Manager 是**唯一有权改变订单状态**的组件。它的状态机设计应该这样处理双源输入：

```
                    ┌──────────────────────┐
  行情流（UDP）───▶│  行情消费器          │
                    │  → 更新客户端订单簿  │
                    │  → 检测到自己的订单  │──── 通知 ──▶┌──────────────┐
                    │    可能被成交         │            │ Order Manager│
                    └──────────────────────┘            │              │
                                                        │ 最终状态机   │
                    ┌──────────────────────┐            │              │
  订单网关（TCP）─▶│  订单网关客户端      │─── 确认 ──▶│              │
                    │  → 解码回报          │            └──────────────┘
                    └──────────────────────┘

  决策规则：
    - 订单网关的 TCP 回报是"权威状态"（the source of truth）
    - 行情检测到的信号是"提前预警"（early detection），用于抢占式更新
```

具体的状态机规则：

| 当前状态 | 行情先告知 | TCP 回报后续到达 | 处理 |
|---|---|---|---|
| `ACTIVE`（订单活跃） | 行情中出现 Trade，价格穿过了挂单价 → 推测可能成交 | "OrderId=X 已成交 Qty=Y" | 提前将订单标记为 `PENDING_EXECUTION`（待确认）。TCP 回报到达后确认为 `FILLED`。如果数量对得上——正常；数量对不上——用 TCP 的数量修正 |
| `PENDING_CANCEL`（撤单已发出，等回复） | 行情显示订单还在 → 撤单可能还未到达 | "撤单成功" | 正常 → `CANCELLED`。如果行情先显示订单没了（被撮合了），标记"可能冲突" |
| `PENDING_CANCEL` | 订单从行情中消失了 | "撤单被拒——已被撮合" | **In-Flight 冲突**。确认状态为 `FILLED` 而非 `CANCELLED`。用 TCP 回报纠正 |

核心原则：**TCP 回报永远是最终仲裁者，行情是加速器**。Order Manager 用两个源各自提供的信息来降低"等待 TCP 回报"带来的延迟窗口，但绝不会用行情信息覆盖 TCP 回报的权威状态。

**（4）这与客户端的 Risk Manager 的关联**

在同步未完成或检测到不一致期间，Risk Manager 会介入：
- 如果某个订单在两个源之间状态不明的状态持续超过阈值（如 100ms），触发"订单状态异常"→ 停止该策略、平仓。
- 如果在行情中检测到大量成交但 TCP 回报迟迟不到 → 可能连接断了 → 紧急关闭策略。
</details>

**Q3：什么是"闪电崩盘"（Flash Crash）？风险管理器如何帮助防范？**

<details>
<summary><b>点击展开答案</b></summary>

**（1）什么是闪电崩盘？**

闪电崩盘（Flash Crash）是指**市场价格在极短时间内（几秒到几分钟）出现剧烈暴跌然后迅速回升**的异常现象。最著名的案例是 2010 年 5 月 6 日美国股灾：道琼斯指数在约 10 分钟内暴跌约 1000 点（约 9%），部分个股甚至跌到接近 0 的价格，然后迅速收复大部分跌幅。

**（2）为什么会发生？—— 四条传导链叠加**

```
① 大单冲击
    └──▶ 一笔异常大的主动卖单入场
           │
           ▼
② 最优价格流动性被吃光 → 价格跳空到下一个档位
    └──▶ 触发 HFT 算法的追跌行为（检测到价格下移 → 加速卖出）
           │
           ▼
③ 做市商撤单（流动性蒸发）
    └──▶ 看到剧烈波动 → 大量撤单 → 订单簿变"空壳"
    └──▶ 剩余订单数量极少、价格极宽
           │
           ▼
④ 连锁止损 + 算法正反馈
    └──▶ 价格下跌触发止损单 → 更多卖单 → 价格再跌 → 更多止损
    └──▶ 形成"死亡螺旋"
```

关键是第 ③ 步：做市商**集体撤单**导致流动性蒸发。一旦订单簿空了，任何一笔小单都能推动价格巨幅跳动。

**（3）风险管理器如何帮助防范？—— 逐条对应**

本节中 Risk Manager 设计了 6 类风险指标（见 5.5.7 节），每条都对 Flash Crash 的某个环节有阻断作用：

| 风控措施 | 阻止的 Flash Crash 环节 | 具体机制 |
|---|---|---|
| **单笔订单最大量** | 阻止 ①（大单冲击） | 限制单笔订单数量上限。如果算法因 bug 试图发 Sell 1,000,000 股，风控直接拒绝发出——从源头防止"胖手指"大单。 |
| **最大持仓** | 阻止 ③（做市商累积过大单边风险） | 做市商双边挂单，如果一侧不断被吃，持仓快速累积。持仓限制让做市商在超过阈值时停止挂新单、只平仓——防止被动累积致命头寸。 |
| **最坏情况持仓** | 阻止 ③ 的加强版 | 不仅看已成交的持仓，还要算上"所有活跃买单如果全部成交会变成多大持仓"。在做市商场景下，如果被动买单不断被吃但尚未成交，最坏情况指标会提前告警。 |
| **盈亏限制（已实现 + 未实现）** | 阻止 ④（连锁止损） | 如果策略亏损达到上限（比如 2%），强制停止所有交易——不让它在崩盘中"越亏越做"。风控不需要理解市场为什么崩盘，只管"损失超线 = 停机"。 |
| **滑动窗口订单频率** | 阻止 ② → ③（算法共振） | 如果检测到单位时间内的发单量异常（说明算法可能在疯狂调整报价或追涨杀跌），暂停交易。这直接打断了 HFT 算法的正反馈环。 |
| **滑动窗口亏损（Rate of Loss）** | 阻止 ④（高速亏损） | 不是"亏了多少"，而是"亏得有多快"。如果在 5 秒内亏损超过阈值，立刻停机——识别出"当前市场不正常"。 |

**在本书架构中的位置**：

```
行情流 → 交易引擎 → 策略决策 → OrderManager.sendOrder()
                         │
                         ▼
                  RiskManager.preTradeCheck()
                    ├── 订单量超限？→ 拒绝
                    ├── 持仓超限？→ 拒绝
                    ├── 亏损超限？→ 拒绝
                    └── 频率超限？→ 拒绝
                         │
                         ▼ 通过
                   订单网关客户端 → 交易所
```

风控检查发生在策略决策和实际发单之间。它是**阻塞门**（gate）：不通过就不能发单。这个检查极快（只是几个变量的比较，纳秒级），不显著增加延迟。

> **核心结论**：风险管理器不能"预测" Flash Crash，但它能阻止你的算法成为 Flash Crash 的**参与者或放大器**——通过限制单笔规模、仓位、亏损和交易频率，在崩盘蔓延到你的策略之前，把策略安全关闭。
</details>

**Q4：为什么 Market Maker 容易受到逆向选择的影响？如何在架构层面减轻？**

<details>
<summary><b>点击展开答案</b></summary>

**（1）先用一个具体例子理解逆向选择**

做市商 A 当前挂的双边报价：
```
Bid: Buy  100 股 @ 10.90     Ask: Sell 100 股 @ 11.00
```

此刻突然传出利好消息（比如苹果财报超预期），市场价格即将跳涨到 11.20。

| 时间 | 发生了什么 | 做市商的处境 |
|---|---|---|
| T0 | 利好消息传出，知情的交易者开始行动 | 做市商的 Ask @11.00 比新的公允价格（~11.20）**低了 0.20** |
| T0+1μs | Liquidity Taker 发现做市商的 Ask 是"过时"的，立即发起主动买单 Buy @11.00 | 做市商的卖单被吃掉：以 11.00 卖了实际值 11.20 的股票 |
| T0+50μs | 做市商收到行情更新，意识到价格变了，赶紧撤掉剩余的 Ask 并挂新高价的 Ask | — |
| T0+5μs 时已成交 | 做市商在这 50μs 的窗口内，以**不利价格**与"比自己信息更快"的人完成了交易 | 这笔交易直接亏损 |

这就是逆向选择：**做市商的公开报价给了知情交易者一个"无风险套利窗口"——在价格变动但做市商还未调整报价的间隙，以过时价格与做市商成交。** 速度快的那一方赢。

**（2）为什么做市商特别容易被逆向选择？—— 三个结构性原因**

| 原因 | 解释 |
|---|---|
| **双向挂单是义务** | 做市商不能选择"只在有利时挂单"，必须持续同时挂买单和卖单。这给了对手方一个"菜单"：你可以选择在任何时候从我这里买或卖。 |
| **报价是公开信息** | 做市商的报价对所有市场参与者可见。对手方可以**有选择性地**只在做市商报价"过时"时才与它交易。 |
| **报价调整有延迟** | 从行情到达网卡到策略计算出新报价再到订单发到交易所，这中间有延迟（即使只有几十微秒）。这个延迟就是"被吃掉"的窗口。 |

**（3）如何在架构层面减轻？—— 不涉及策略逻辑，只谈系统架构**

"架构层面"指的是你可以改组件边界、线程排布、通信方式、硬件部署——**不碰策略逻辑本身**。以下是四个维度的架构设计：

---

**维度一：全链路延迟——缩小"被吃"的时间窗口**

逆向选择的时间窗口 = 行情到达交易所 → 你做市商收到行情 → 策略反应 → 新报价/撤单到达交易所。**你的全链路延迟比对手短，你就不会被它对你的逆向选择打败**。

```
行情到达你的网卡
    │── T1: 网卡 → 用户态（kernel bypass？）
    │── T2: 行情解码（reinterpret_cast 还是字符串解析？）
    │── T3: 订单簿更新（无锁队列 → 策略线程）
    │── T4: 策略计算新报价（CPU 计算）
    │── T5: 撤单/改单请求编码（packed struct）
    │── T6: 订单网关客户端发送（TCP send）
    └── 到达交易所

总延迟 = T1+T2+T3+T4+T5+T6
```

架构层面的优化路径：

| 环节 | 架构手段 | 第四章对应 |
|---|---|---|
| T1（网卡→用户态） | Kernel bypass（OpenOnload / DPDK），网卡 DMA 直接到用户态内存，不经过内核协议栈 | 第 4 章网络 socket 封装 |
| T2（解码） | 二进制 packed 协议，直接在收包 buffer 上 `reinterpret_cast` | 第 5 章行情协议设计 |
| T3（线程间传递） | SPSC 无锁队列（`memory_order_acquire/release`），行情线程 → 策略线程延迟为一个原子变量写入 | 第 4 章无锁队列 |
| T4（策略计算） | 策略线程绑定到隔离核心，用 `pthread_setaffinity_np`，避免调度抖动 | 第 4 章线程亲和性 |
| T5（编码） | 预分配的固定 buffer，不调 `new` | 第 4 章内存池 |
| T6（发单到交易所） | Co-location（托管在交易所机房，光纤几十米内），静态链接，无锁 | 第 2 章 + 第 4 章 |

---

**维度二：组件独立性——不让非关键任务拖累反应速度**

```
行情消费器线程  ──SPSC 队列──▶  策略决策线程  ──SPSC 队列──▶  订单网关客户端线程
（独立 CPU 核心）              （隔离 CPU 核心）              （独立 CPU 核心）
```

| 架构决策 | 防逆向选择的效果 |
|---|---|
| 策略线程独占隔离核心（`isolcpus` + `nohz_full`） | 策略线程不会被日志刷新、TCP 心跳、UDP 接收等中断干扰——从收到行情到发出新报价的延迟**确定且最低** |
| 行情消费和策略决策分线程 | 行情消费只做解码和订单簿更新（CPU 轻），不做策略逻辑。两者解耦后，行情处理线程的延迟不易受策略计算时间抖动的影响 |
| Risk Manager 与策略同步（不跨线程） | 风控检查只是几个数字比较，在策略线程内联执行。如果风控独立成一个需要 RPC 的服务，每次发单前跨线程或跨机器查询——增加不可预测的延迟 |

---

**维度三：数据流设计——减少拷贝、减少间接访问**

| 数据流设计 | 防逆向选择的效果 |
|---|---|
| 行情直接在接收 buffer 上解码（in-place），不拷贝 | 零拷贝 → 行情到达和应用层解码之间的延迟最小 |
| 策略的订单簿与行情线程的订单簿共享同一块内存（但用无锁同步） | 策略看到的订单簿始终是最新状态，不需要等待"更新通知"
| 订单对象从内存池获取 | 分配延迟确定性高，策略发单不会被 `new` 的系统调用阻塞 |

---

**维度四：物理架构——Co-location**

软件架构做到极致后，物理距离成为剩余延迟的主要来源。Co-location 是做市商对抗逆向选择的最强架构武器：

```
Co-location 之前：
  做市商服务器 ─── 200 公里光纤 ───▶ 交易所服务器
  光是光纤单向传输就 ~1ms（光速 200km/μs ÷ 1.5 折射率）

Co-location 之后：
  做市商服务器（交易所机房同一机架）── 10 米光纤 ──▶ 交易所服务器
  光纤传输 ~50ns

差距：~950μs → 就是逆向选择窗口被缩小了 950μs
```

---

**总结：架构层面的逆向选择防御 = 缩短"全链路反应时间"**

逆向选择不是一个策略能解决的问题——它是物理定律。**你无法消除"对方知道得比你早"这件事，但你可以把"对方比你早"的时间差从毫秒压到微秒**。系统性架构设计（kernel bypass + lock-free + thread pinning + binary protocol + co-location）共同作用，把这个窗口缩到最小。

</details>

## 五、常见误区与注意事项

| 误区 | 正确认识 |
|---|---|
| ❌ "撮合引擎就是订单簿" | ✅ 订单簿是撮合引擎内部维护的数据结构，撮合引擎还包含匹配逻辑、组件通信等 |
| ❌ "行情数据用 UDP 就不需要确认了" | ✅ 需要序列号 + 快照恢复机制来弥补 UDP 的不可靠性 |
| ❌ "客户端订单簿和交易所订单簿完全一样" | ✅ 客户端看不到订单所属方，并且有传输延迟 |
| ❌ "FIFO 排序器是无关紧要的组件" | ✅ 它保证了市场公平性——先到的订单先被处理 |
| ❌ "Feature Engine 必须很复杂" | ✅ 可以根据策略需求从简开始；本书只有两个简单特征 |
| ❌ "Order Manager 就是发单和收回报" | ✅ 它需要处理大量 in-flight 冲突情况（撤单 vs 撮合 etc.） |
| ❌ "风险控制会拖慢系统" | ✅ 合理的设计（独立线程、预计算）可以将风控延迟降到很低 |
