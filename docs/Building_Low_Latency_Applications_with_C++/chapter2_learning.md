## 三、学习路线（分 5 个小节）

### 第 1 小节：实时视频直播的低延迟设计

#### 3.1.1 核心概念

**Glass-to-glass latency（端到端玻璃延迟）**：
- 从摄像头捕捉到画面，到观众屏幕显示出来所经过的时间。
- 这个名字很形象：从一块“玻璃”（摄像头镜头）到另一块“玻璃”（屏幕）。

**Video Distribution Service（VDS）**：
- 负责把多路音视频流分发给观众的系统。
- 最常见的 VDS 就是 **CDN（Content Delivery Network，内容分发网络）**。

**三个重要处理过程**：

| 术语 | 含义 |
|---|---|
| **Transcoding（转码）** | 把视频从一种编码格式转换为另一种，可能改变编码器、分辨率、采样率等 |
| **Transmuxing（复用转换）** | 只改变封装格式，不改变视频本身的编码 |
| **Transrating（转码率）** | 改变视频码率，通常是为了适配不同带宽 |

#### 3.1.2 视频流的 glass-to-glass 链路

```
摄像头采集 → 音视频封装 → 编码/转码/转码率 → 网络传输 → CDN 分发 → 接收端缓冲 → 解码 → 渲染显示
```

这个链路上的每一步都可能引入延迟：

| 步骤 | 延迟来源 |
|---|---|
| 采集设备 | 摄像头、采集卡的硬件处理时间 |
| 编码器 | 转码、转码率、压缩算法的 CPU/硬件开销 |
| 网络传输 | 物理距离、路由跳数、带宽、拥塞 |
| CDN 分发 | 节点负载、缓存策略、回源延迟 |
| 接收端缓冲 | Jitter buffer 为了平滑网络抖动而引入的缓冲 |
| 解码渲染 | 播放器缓冲 segment（通常 2–10 秒）、设备性能 |

#### 3.1.3 延迟来源详解

1. **物理距离与网络质量**
   - 距离越远，光/电信号传播时间越长。
   - 网络带宽不足或不稳定会导致缓冲、重传、卡顿。

2. **采集与编码硬件**
   - 编码器需要先把原始视频缓冲、解码、处理、再编码。
   - 软件编码 vs 硬件编码（如 BoxCaster、Teradek）延迟差异很大。

3. **流媒体协议与 jitter buffer**
   - 协议选择决定延迟下限。
   - 网络包可能乱序、丢包、延迟到达，接收端用 jitter buffer 平滑，但这会增加延迟。

4. **码率与分段长度**
   - 低码率意味着单位时间传输数据少，延迟低，但画质差。
   - HTTP-based 协议把流切成 2–10 秒的 segment，播放器要等一个完整 segment 才能播放。
   - iOS 播放器通常会缓冲 3–5 个 segment 才开始播放。

#### 3.1.4 延迟的影响

| 问题 | 说明 |
|---|---|
| 音视频质量下降 | 为了降延迟过度压缩，画面模糊、声音失真 |
| 缓冲卡顿 | 网络跟不上，频繁 pause 缓冲 |
| 音视频不同步 | 音频数据小，先到；视频数据大，后到 |
| 快进/回放不流畅 | 高延迟导致重新同步困难 |

#### 3.1.5 视频流技术协议对比

**Non-HTTP-based 协议**：

| 协议 | 特点 |
|---|---|
| **RTSP** | 应用层协议，支持播放控制，但兼容性差，已逐渐被淘汰 |
| **RTMP / Flash** | 曾经流行，低延迟，但 Flash 因安全问题被弃用，扩展性有限 |

- 优点：可以达到较低延迟。
- 缺点：扩展性差，不支持现代自适应码率（ABR），浏览器兼容性差。

**HTTP-based 协议**：

| 协议 | 特点 |
|---|---|
| **HLS（HTTP Live Streaming）** | 最广泛支持，可扩展性强，Low Latency HLS（LL-HLS）可做到 < 2 秒 |
| **DASH（Dynamic Adaptive Streaming over HTTP）** | MPEG 标准，类似 HLS，支持 chunked encoding/transfer |
| **CMAF（Common Media Application Format）** | 不是新格式，而是统一封装，兼容 HLS/DASH，降低存储和延迟 |
| **HESP** | 超低延迟（<500ms），用 initialization + continuation 双流，但成本高 |
| **WebRTC** | P2P 协议，亚秒级延迟，支持浏览器原生，但工程复杂、扩展性有挑战 |

> **关键权衡**：HTTP-based 协议牺牲一点延迟，换取可扩展性、兼容性和 ABR 能力。

#### 3.1.6 代码示例：感受 segment 长度对延迟的影响

```cpp
#include <iostream>

int main() {
    // 不同 segment 长度（秒）
    const int segment_lengths[] = {2, 5, 10};
    // iOS 通常缓冲 3-5 个 segment
    const int buffered_segments = 4;
    
    for (int seg_len : segment_lengths) {
        int player_delay = seg_len * buffered_segments;
        std::cout << "segment 长度: " << seg_len << " 秒, "
                  << "播放器缓冲延迟: " << player_delay << " 秒\n";
    }
    
    return 0;
}
```

> **思考点**：
> 1. 为什么 HTTP-based 视频流的延迟下限至少是一个 segment 的长度？
> 2. WebRTC 为什么能做到亚秒级延迟？它放弃了什么？
> 3. 在直播平台（如 Twitch）和视频会议（如 Zoom）之间，对延迟的要求有什么不同？

<details>
<summary><b>思考点答案</b></summary>

1. **为什么 HTTP-based 视频流的延迟下限至少是一个 segment 的长度？**
   - HTTP-based 协议把连续音视频流切分成固定时长的 segment（如 2–10 秒）。
   - 播放器必须收到一个**完整 segment** 后才能开始解码和播放。
   - 即使网络很快，segment 还没生成完，播放器也只能等。
   - 有些播放器（如 iOS）为了平滑，会缓冲 3–5 个 segment，延迟就是几倍 segment 长度。
   - 所以这类协议天然有“segment 级”延迟，无法做到真正的实时。

2. **WebRTC 为什么能做到亚秒级延迟？它放弃了什么？**
   - WebRTC 是 P2P 协议，端与端直接通信，不需要经过 CDN 分段的中间环节。
   - 它使用 UDP（SRTP）传输音视频，不需要像 TCP 那样等待确认。
   - 它采用小 packet、自适应码率、jitter buffer 优化等技术。
   - **放弃的**：
     - 大规模广播能力：P2P 连接数受限，大规模直播需要 SFU/MCU 服务器。
     - 可靠性：UDP 不保证到达，需要自己处理丢包、抖动。
     - 易用性：工程复杂，涉及 NAT 穿透、信令、加密、多种子协议。

3. **直播平台与视频会议对延迟的要求有什么不同？**
   - **直播平台（Twitch）**：
     - 主要是单向广播，观众和主播实时互动要求不高。
     - 关注可扩展性，可能有几万甚至上百万观众。
     - 延迟 3–10 秒可接受。
   - **视频会议（Zoom）**：
     - 双向/多向实时互动，需要轮询发言、即时反馈。
     - 延迟必须低于人的感知阈值（约 150–400 ms）。
     - 使用 WebRTC 等亚秒级技术。
   - 这解释了为什么两者会选择不同的技术栈。

</details>

### 第 2 小节：游戏应用的低延迟设计

#### 3.2.1 为什么游戏对延迟敏感？

现代游戏的特点：
- 全球多人在线
- 高画质、复杂物理、AI
- AR/VR 对延迟要求极高
- 移动端云游戏对网络依赖更强

游戏中的延迟通常称为 **ping latency**，即客户端到服务器再返回的往返时间。

| 应用场景 | 可接受延迟 |
|---|---|
| 休闲游戏 | 100–300 ms |
| 竞技网游 | < 50 ms |
| FPS / 格斗游戏 | < 20–30 ms |
| VR / 云游戏 | < 20 ms，最好 < 10 ms |

#### 3.2.2 游戏延迟来源

1. **输入设备延迟**
   - 鼠标、键盘、手柄的采集和传输时间。
   - 高刷新率显示器、低延迟输入设备可以减少这部分。

2. **渲染管线延迟**
   - CPU 逻辑计算 → GPU 渲染 → 显示器输出。
   - 高帧率（如 120Hz/240Hz）能降低帧间等待时间。

3. **网络传输延迟**
   - 客户端与服务器之间的物理距离、路由、拥塞。
   - 数据包在服务器处理后再返回客户端。

4. **服务器处理延迟**
   - 游戏状态同步、物理模拟、反作弊检测。
   - 服务器负载高时处理变慢。

5. **显示输出延迟**
   - 显示器的刷新率和响应时间。
   - G-Sync / FreeSync 等技术可以减少画面撕裂和输入延迟。

#### 3.2.3 游戏优化方向

| 方向 | 具体手段 |
|---|---|
| **硬件升级** | 更强的 CPU/GPU、SSD、高刷新率显示器、低延迟外设 |
| **游戏设置优化** | 降低画质、关闭垂直同步、降低分辨率、关闭抗锯齿/特效 |
| **网络优化** | 选择近距离服务器、优化路由、使用 UDP、预测/补偿技术 |
| **系统优化** | 更新显卡驱动、关闭后台程序、使用游戏模式 |
| **软件架构优化** | 客户端预测、服务器 reconciliation、插值/外推 |

#### 3.2.4 代码示例：简单模拟客户端预测

```cpp
#include <iostream>
#include <chrono>
#include <thread>

// 模拟玩家位置
struct Player {
    double x = 0.0;
    double y = 0.0;
    double vx = 1.0;  // 速度 x
    double vy = 0.5;  // 速度 y
};

// 客户端预测：根据本地输入立即更新位置
void client_predict(Player& p, double dt) {
    p.x += p.vx * dt;
    p.y += p.vy * dt;
}

// 服务器权威状态：过一段时间才到达
void server_authoritative(Player& p, double dt) {
    p.x += p.vx * dt;
    p.y += p.vy * dt;
}

int main() {
    Player local;
    Player server;
    
    const double dt = 0.016;  // 约 60 FPS
    
    // 模拟 10 帧
    for (int i = 0; i < 10; ++i) {
        // 客户端立刻响应输入
        client_predict(local, dt);
        
        // 服务器有延迟，但仍是权威
        std::this_thread::sleep_for(std::chrono::milliseconds(5));
        server_authoritative(server, dt);
        
        // 当服务器状态到达后，客户端进行 reconciliation
        if (i == 9) {
            std::cout << "本地预测位置: (" << local.x << ", " << local.y << ")\n";
            std::cout << "服务器权威位置: (" << server.x << ", " << server.y << ")\n";
            
            // 如果差异不大，直接插值；如果差异大，需要回滚重放
            double dx = local.x - server.x;
            double dy = local.y - server.y;
            std::cout << "差异: (" << dx << ", " << dy << ")\n";
        }
    }
    
    return 0;
}
```

> **思考点**：
> 1. 为什么游戏中常用“客户端预测 + 服务器权威 + 回滚重放”？
> 2. 为什么竞技游戏通常使用 UDP 而不是 TCP？
> 3. 云游戏相比本地游戏多了哪些延迟来源？

<details>
<summary><b>思考点答案</b></summary>

1. **为什么用“客户端预测 + 服务器权威 + 回滚重放”？**
   - **客户端预测**：玩家按下按键后，本地立刻显示结果，避免等待服务器往返，提升手感。
   - **服务器权威**：防止外挂，服务器保存真实游戏状态，客户端不能随意修改。
   - **回滚重放（Reconciliation）**：当服务器权威状态到达后，如果与本地预测不一致，客户端需要修正。
     - 差异小：直接插值平滑修正。
     - 差异大：回滚到旧状态，重新应用本地输入序列。
   - 这种架构在“手感”和“公平性”之间取得平衡。

2. **为什么竞技游戏用 UDP 而不是 TCP？**
   - TCP 为了保证可靠性，会重传丢包、保证顺序，这会引入不可预测的延迟抖动。
   - 游戏中，旧的位置信息即使重传到达也没用了，玩家更关心最新的状态。
   - UDP 不保证顺序和可靠到达，但延迟低、可控性强。
   - 游戏可以在 UDP 之上实现自定义的可靠性策略：重要的信息（如开枪命中）可以确认，不重要的信息（如位置更新）可以丢弃旧包。

3. **云游戏多了哪些延迟来源？**
   - **输入上传**：玩家操作要传到云端服务器。
   - **云端渲染**：服务器运行游戏并编码视频流。
   - **视频流下传**：把渲染好的视频帧传回客户端。
   - **客户端解码**：客户端解码并显示视频。
   - 整个链路叠加起来，延迟通常比本地游戏高 50–200 ms。
   - 这也是为什么云游戏对网络质量、数据中心位置、视频编码效率要求极高。

</details>

### 第 3 小节：IoT 与零售分析的低延迟设计

#### 3.3.1 IoT 的典型场景

- 远程巡检（无人机、桥梁/隧道监控）
- 自动驾驶汽车数据采集
- 农业自动化、物流追踪、仓库管理
- 智能零售（库存、客流、供应链分析）
- 工业设备监控与预测性维护

#### 3.3.2 IoT 延迟来源

1. **设备端采集与处理**
   - 传感器采样率、MCU/嵌入式芯片性能。
   - 边缘预处理 vs 直接上传原始数据。

2. **网络传输**
   - 无线信号质量、基站距离、协议开销。
   - 4G/5G/Wi-Fi/LoRa 等不同网络的选择。

3. **云端处理**
   - 数据上传到云端服务器，处理后再返回结果。
   - 距离远、云端负载高都会增加延迟。

4. **数据存储与分析**
   - 海量设备数据写入数据库、触发分析 pipeline。
   - 批量处理 vs 流式处理。

#### 3.3.3 低延迟 IoT 的关键技术

| 技术 | 作用 |
|---|---|
| **P2P 直连** | 设备之间直接通信，不经过云端，减少中间跳转 |
| **5G** | 提供高带宽、低延迟、高可靠的无线连接 |
| **边缘计算（Edge Computing）** | 把计算和存储放在靠近数据源的地方 |
| **AI 边缘推理** | 在边缘设备上直接跑 AI 模型，减少云端往返 |
| **近端部署（Proximity）** | 把处理节点部署在离设备和用户最近的位置 |

#### 3.3.4 边缘计算详解

**传统模式**：
```
设备 → 云端 → 处理 → 返回结果
```
- 数据来回传输，距离远，延迟高。
- 带宽成本高，隐私性差。

**边缘计算模式**：
```
设备 → 边缘网关/服务器 → 本地处理 → 返回结果
```
- 处理靠近数据源，延迟低。
- 减少核心网带宽压力。
- 支持实时决策。

**5G + 边缘计算**：
- 5G 提供低延迟无线接入。
- 边缘计算提供近端处理能力。
- 两者结合才能发挥最大价值。
- 没有边缘计算的 5G，数据还是要跑很远去处理，延迟优势被抵消。

#### 3.3.5 代码示例：模拟云端 vs 边缘处理的延迟

```cpp
#include <iostream>
#include <chrono>
#include <thread>

// 模拟云端处理：距离远，延迟高
void cloud_process(int data) {
    // 网络往返 100ms + 云端处理 20ms
    std::this_thread::sleep_for(std::chrono::milliseconds(120));
    std::cout << "云端处理完成，结果: " << data * 2 << "\n";
}

// 模拟边缘处理：距离近，延迟低
void edge_process(int data) {
    // 本地网络 5ms + 边缘处理 15ms
    std::this_thread::sleep_for(std::chrono::milliseconds(20));
    std::cout << "边缘处理完成，结果: " << data * 2 << "\n";
}

int main() {
    using namespace std::chrono;
    
    int sensor_data = 42;
    
    // 云端处理耗时
    auto start = high_resolution_clock::now();
    cloud_process(sensor_data);
    auto end = high_resolution_clock::now();
    std::cout << "云端总延迟: " << duration_cast<milliseconds>(end - start).count() << " ms\n\n";
    
    // 边缘处理耗时
    start = high_resolution_clock::now();
    edge_process(sensor_data);
    end = high_resolution_clock::now();
    std::cout << "边缘总延迟: " << duration_cast<milliseconds>(end - start).count() << " ms\n";
    
    return 0;
}
```

> **思考点**：
> 1. 为什么 IoT 强调“近端部署（proximity）”？
> 2. 边缘计算相比纯云端有哪些优势和劣势？
> 3. 5G 和边缘计算是什么关系？为什么两者要配合？

<details>
<summary><b>思考点答案</b></summary>

1. **为什么 IoT 强调近端部署？**
   - IoT 设备数量巨大，产生海量数据。
   - 如果所有数据都传到 distant cloud，延迟高、带宽成本高、可靠性差。
   - 很多 IoT 场景需要实时决策（如自动驾驶、工业控制），不能等数据往返云端。
   - 把计算和存储放在靠近设备的地方（边缘），可以：
     - 显著降低延迟
     - 减少骨干网带宽消耗
     - 提高隐私和安全性
     - 在弱网环境下也能工作

2. **边缘计算的优势和劣势**
   - **优势**：
     - 低延迟
     - 减少带宽成本
     - 数据隐私更好
     - 可靠性高（不依赖远端云）
     - 可扩展性好（分散处理压力）
   - **劣势**：
     - 部署和管理复杂
     - 边缘节点计算资源有限
     - 安全边界扩大，需要保护更多节点
     - 数据一致性、故障恢复更复杂
     - 初始建设成本高

3. **5G 和边缘计算的关系**
   - **5G 解决的是接入问题**：提供设备到边缘节点的高速、低延迟、高可靠无线连接。
   - **边缘计算解决的是处理问题**：让数据在靠近源头的位置被处理，不用远赴云端。
   - **两者互补**：
     - 只有 5G 没有边缘计算：数据到达基站后还要跑很远去处理，延迟优势被抵消。
     - 只有边缘计算没有 5G：设备到边缘的接入可能延迟高、带宽低。
   - 所以 5G 在设计时就考虑了 IoT 和边缘计算场景。

</details>

### 第 4 小节：电子交易的低延迟设计（重点）

#### 3.4.1 为什么电子交易对延迟极度敏感？

现代电子市场中，交易机会**极其短暂**。

- 谁能更快处理行情、发现机会、发送订单，谁就能盈利。
- 反应慢不仅赚得少，还可能**站在错误的一边亏钱**。
- 这种对延迟的极致追求被称为 **HFT（High-Frequency Trading，高频交易）的“军备竞赛”**。

#### 3.4.2 做市商 vs 流动性提取者

这是电子交易中最基本的两种角色：

| 角色 | 行为 | 对延迟的敏感度 |
|---|---|---|
| **Market Maker（做市商）** | 持续挂出买单和卖单，提供流动性 | 极高，需要快速调整报价 |
| **Liquidity Taker（流动性提取者）** | 等待机会，主动吃单 | 极高，需要抢在别人前面 |

**例子**：
- 市场行情即将上涨。
- 做市商需要**快速取消或上移自己的卖单**，避免被低价买走。
- 流动性提取者希望**快速发送买单**，抢到做市商的卖单。
- 谁更快，谁就赢。

#### 3.4.3 延迟对交易收入的影响

1. **抢不到机会**
   - 更快的参与者先成交，慢的人只能看着机会消失。

2. **逆向选择（Adverse Selection）**
   - 做市商反应慢，没来得及撤单，被流动性提取者以旧价格成交。
   - 市场价格已经变了，做市商被迫以不利价格交易。

3. **风控延迟**
   - 实时风险管理系统需要跟踪大量产品和交易所的头寸、盈亏。
   - 风控延迟可能导致无法及时止损或关闭超限策略。

#### 3.4.4 实现超低延迟的常见手段

| 方向 | 具体手段 |
|---|---|
| **硬件优化** | 高性能服务器、大缓存 CPU、低延迟网卡、专用交换机 |
| **Kernel Bypass** | 绕过内核协议栈，直接操作网卡，如 Solarflare OpenOnload / ef_vi / TCPDirect |
| **网络优化** | 近距离托管（co-location）、优化路由、低延迟交换机 |
| **避免系统调用** | 热路径不上内核、使用用户态驱动 |
| **避免动态内存分配** | 预分配、内存池、对象复用 |
| **无锁数据结构** | lock-free queue、atomic、per-thread 设计 |
| **线程亲和性** | 把线程绑定到指定 CPU 核心，减少调度抖动 |
| **静态链接** | 编译时把所有依赖库链接进二进制，避免运行时加载和解析 |
| **编译时计算** | 用 constexpr / 模板把能提前算的都提前算 |
| **FPGA / 专用硬件** | 把关键逻辑固化到芯片，可达亚微秒级（本书不讲 FPGA） |

#### 3.4.5 关键硬件概念

| 概念 | 说明 |
|---|---|
| **NUMA（Non-Uniform Memory Access）** | 多路 CPU 架构中，访问本地内存快，访问远端内存慢。需要把线程和内存绑定到同一 NUMA 节点。 |
| **CPU 缓存层次** | L1 < L2 < L3，缓存越大、越近越快，但越贵。 |
| **超线程（Hyperthreading）** | 一个物理核模拟两个逻辑核，可能共享资源导致干扰。低延迟场景常关闭。 |
| **Kernel Bypass NIC** | 网卡直接把数据送到用户态，避免内核协议栈拷贝和系统调用。 |
| **Switching Latency** | 交换机收到包到转发出去的时间，通常几十到几百纳秒。 |

#### 3.4.6 多线程的权衡

- 多线程可以提高吞吐，但不一定降低延迟。
- 线程间同步（锁、信号量）会引入延迟和上下文切换。
- 理想状态：线程被固定在指定核心上，几乎不被调度出去，一直在用户态运行。
- 本书后续会采用：**每个核心一个线程、per-thread 数据结构、无锁队列传递数据**。

#### 3.4.7 动态内存分配的危害

- `new`/`delete` 会请求操作系统查找空闲内存块。
- 运行时间久了，内存碎片化，查找时间变长。
- 分配和释放发生在关键路径上，每次都有开销。
- C++ 允许我们完全控制内存：预分配、内存池、arena allocator。

#### 3.4.8 静态链接 vs 动态链接

| 方式 | 优点 | 缺点 |
|---|---|---|
| **动态链接** | 二进制小，多个程序共享库，更新方便 | 运行时首次调用需解析，无法做跨库优化 |
| **静态链接** | 无运行时加载开销，编译器可全局优化，启动快 | 二进制大，每个程序都包含库副本 |

- 超低延迟交易系统通常使用**静态链接**。

#### 3.4.9 代码示例：模拟订单响应延迟对盈亏的影响

```cpp
#include <iostream>
#include <chrono>
#include <thread>
#include <random>

// 模拟一次交易机会
struct Opportunity {
    double fair_price = 100.0;   // 公允价格
    double bid_price = 99.95;    // 买单价
    double ask_price = 100.05;   // 卖单价
    int lifetime_us = 50;        // 机会存在时间（微秒）
};

// 模拟发送订单的延迟
bool try_trade(const Opportunity& opp, int latency_us, bool is_taker) {
    // 延迟越大，机会消失的概率越高
    std::this_thread::sleep_for(std::chrono::microseconds(latency_us));
    
    // 简单模型：如果延迟超过机会寿命的一半，成功率下降
    double success_prob = 1.0 - static_cast<double>(latency_us) / (opp.lifetime_us * 2.0);
    if (success_prob < 0.0) success_prob = 0.0;
    
    std::mt19937 rng(latency_us);
    std::uniform_real_distribution<double> dist(0.0, 1.0);
    
    return dist(rng) < success_prob;
}

int main() {
    Opportunity opp;
    
    // 不同延迟的参与者
    int latencies[] = {5, 20, 50, 100};
    
    for (int lat : latencies) {
        int wins = 0;
        int trials = 1000;
        for (int i = 0; i < trials; ++i) {
            if (try_trade(opp, lat, true)) {
                wins++;
            }
        }
        std::cout << "延迟 " << lat << " us, 成交率: "
                  << (100.0 * wins / trials) << "%\n";
    }
    
    return 0;
}
```

> **思考点**：
> 1. 为什么电子交易中常说“延迟直接等于收入”？
> 2. Kernel bypass 为什么能显著降低网络延迟？它绕过了什么？
> 3. 为什么超低延迟系统倾向于静态链接而不是动态链接？
> 4. 多线程一定能降低交易延迟吗？什么情况下会适得其反？

<details>
<summary><b>思考点答案</b></summary>

1. **为什么“延迟直接等于收入”？**
   - 电子市场中的套利、做市等机会存活时间极短，可能只有微秒级。
   - 同一个机会，多个参与者在竞争。
   - 最快成交的参与者拿到利润，慢的人可能完全错过。
   - 对做市商而言，反应慢还意味着被“逆向选择”：价格已经变了，但自己的旧报价还没撤，被更快的人以旧价格成交，造成亏损。
   - 因此，延迟不仅是性能指标，更是直接的盈利能力指标。

2. **Kernel bypass 为什么能降低网络延迟？它绕过了什么？**
   - 传统网络路径：网卡 → 内核协议栈 → 系统调用 → 用户态程序。
   - 每一步都有开销：中断、数据拷贝、上下文切换、协议处理。
   - Kernel bypass：网卡直接把数据映射到用户态内存，应用程序直接读写网卡。
   - 绕过的是：内核 TCP/IP 协议栈、`recv()`/`send()` 系统调用、内核与用户态之间的数据拷贝。
   - 典型产品：Solarflare OpenOnload、ef_vi、TCPDirect、Exablaze 等。
   - 可以把网络延迟从几十微秒降到几微秒甚至亚微秒。

3. **为什么倾向静态链接？**
   - 动态链接在程序启动或首次调用时需要解析和加载共享库，有运行时开销。
   - 动态链接的库代码边界会阻止编译器做跨模块优化（如内联、死代码消除）。
   - 静态链接把所有代码合并到一个二进制中：
     - 启动更快
     - 编译器可以做全局优化
     - 没有运行时依赖解析
   - 超低延迟系统把每个微秒都当回事，所以通常选择静态链接。

4. **多线程一定能降低延迟吗？**
   - **不一定**。
   - 多线程提高的是**吞吐**（单位时间处理更多事），不是必然降低**单条路径延迟**。
   - 如果线程间需要共享数据，就必须同步：
     - 锁竞争会导致等待
     - 上下文切换会保存/恢复线程状态
     - 锁底层可能调用内核（futex），进入内核态开销大
   - 在 HFT 中，常见做法是：
     - 尽量减少共享状态
     - 使用无锁数据结构
     - 把线程绑定到指定核心
     - 让线程尽可能不被调度出去
   - 本书后续会采用 SPSC lock-free queue、per-thread 设计等方式来兼顾并行和低延迟。

</details>

### 第 5 小节：跨场景的共性规律

#### 3.5.1 不同场景的延迟容忍度

| 场景 | 可接受延迟 | 关键优化方向 |
|---|---|---|
| 视频直播 | 1–5 秒 | 协议选择、CDN、码率自适应 |
| 视频会议 | < 500 ms | WebRTC、P2P、jitter buffer |
| 在线游戏 | 20–100 ms | UDP、预测/补偿、就近服务器 |
| IoT | 毫秒级到秒级 | 边缘计算、5G、P2P |
| 电子交易 | 微秒级 | 硬件、kernel bypass、无锁、静态链接 |

#### 3.5.2 共通的延迟来源

无论哪个场景，延迟通常来自：

1. **物理距离**：光/电传播需要时间。
2. **网络质量**：带宽、拥塞、丢包、抖动。
3. **中间节点**：服务器、网关、CDN、交换机、路由器。
4. **数据拷贝**：用户态 ↔ 内核态、内存 ↔ 设备。
5. **协议开销**：握手、确认、重排、分包。
6. **处理时间**：编码、解码、压缩、加密、业务逻辑。
7. **同步等待**：锁、缓冲、排队、调度。

#### 3.5.3 共通的优化思路

| 思路 | 具体做法 |
|---|---|
| **减少距离** | 就近部署、边缘计算、co-location |
| **减少拷贝** | kernel bypass、zero-copy、内存映射 |
| **减少等待** | 无锁数据结构、预分配、异步处理 |
| **减少处理** | 编译时计算、硬件加速、简化协议 |
| **减少抖动** | 线程绑定、禁用节能、专用硬件 |

## 五、常见误区与注意事项

| 误区 | 正确认识 |
|---|---|
| ❌ “所有场景都需要最低延迟” | ✅ 不同业务对延迟容忍度不同，要按场景选择 |
| ❌ “HTTP-based 协议一定慢” | ✅ 它用可控延迟换取可扩展性，很多场景是更优选择 |
| ❌ “多线程一定更快” | ✅ 多线程提高吞吐，但可能增加单路径延迟 |
| ❌ “Kernel bypass 适合所有应用” | ✅ 它复杂度高，只在 latency-critical 核心路径使用 |
| ❌ “硬件越贵延迟越低” | ✅ 硬件是基础，但架构和代码同样关键 |

## 八、本章核心金句

> “低延迟设计的第一步不是选技术，而是理解业务场景和延迟来源。”

> “电子交易中，延迟不是成本，而是收入。”

> “不同场景对延迟的容忍度不同，但底层的延迟来源和优化思想是相通的。”

> “边缘计算的核心不是‘在边缘算’，而是‘把计算放在离数据和用户最近的地方’。”
