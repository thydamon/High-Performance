# 虚拟内存与页表映射原理详解

> 目标：理解虚拟内存为何能"夸大承诺"给每个进程分配远大于物理内存的地址空间，以及页表如何把虚拟地址翻译为物理地址。

---

## 一、虚拟内存是什么？

**虚拟内存 = 一个"翻译中间层"**

每个进程看到的内存地址，不是真实的物理内存地址，而是经过一层翻译的"虚拟地址"。这层翻译由操作系统 + CPU 的 **MMU（Memory Management Unit，内存管理单元）** 共同完成。

```
进程 A 眼中的地址空间:              实际物理内存:
  0x00007f001000          ──┐         ┌─ 0x3a2f1000 (物理页帧)
  0x00007f002000          ──┤         │
  0x00007f003000          ──┼─翻译──→ │
  0x00007f004000          ──┼─翻译──→ ├─ 0x5b8c4000 (物理页帧)
  0x00007f005000          ──┼─翻译──→ │
  0x00007f006000          ──┘         └─ 0x7f1e9000 (物理页帧)
```

关键事实：

- 进程 A 看到的地址空间是**连续的、独立的**；
- 实际物理内存中，进程 A 的数据可能散落在完全不连续的位置；
- **每个进程有自己独立的虚拟地址空间**，互相看不见对方的内存；
- 虚拟地址空间中大部分区域是**未映射的空洞**，不占用任何物理资源。

---

## 二、进程虚拟地址空间布局

64 位 Linux x86-64 下，虽然虚拟地址理论上有 64 位，但实际有效位只有 48 位（256TB）：

```
进程的虚拟地址空间（64位，48位有效）:

0x0000000000000000 ┌──────────────────┐
                   │  NULL (不可访问)   │  128TB (用户空间)
                   │                   │
                   │  代码段 (Text)     │  ← 程序的机器指令
                   │  数据段 (Data)     │  ← 全局变量、静态变量
                   │  BSS 段           │  ← 未初始化的全局变量
                   ├──────────────────┤
                   │  堆 (Heap)        │  ← brk() / sbrk() 控制，向上增长
                   │  ↓               │
                   │                   │
                   │  (空洞)           │
                   │                   │
                   │  ↑               │
                   │  动态映射区       │  ← mmap() 分配、共享库映射
                   │  ↓               │
                   │                   │
                   │  (空洞)           │
                   │                   │
                   │  ↑               │
                   │  栈 (Stack)       │  ← 向下增长，函数调用、局部变量
                   │                   │
0x00007FFFFFFFFFFF ├──────────────────┤
                   │  内核空间          │  128TB（所有进程共享同一套内核页表）
0xFFFFFFFFFFFFFFFF └──────────────────┘
```

各个区域的增长方向：

- **栈**：从高地址向低地址增长（函数调用压栈）；
- **堆**：从低地址向高地址增长（`brk()` / `sbrk()` 扩展）；
- **mmap 区**：在堆和栈之间，按需从两边向中间推进。

## 三、为什么 16GB 物理内存能给每个进程分配 16GB 虚拟内存？

**核心答案：虚拟地址 ≠ 物理地址，而且大多数虚拟地址根本没有对应的物理内存。**

### 原因 1：按需分配（Lazy Allocation / Demand Paging）

操作系统"承诺"了地址空间，但**不立即兑现物理内存**：

```
进程调用 mmap(16GB):

  虚拟地址空间:  分配了 16GB 的"地址范围"  ← 只是记账，零物理内存消耗
  物理内存:      分配了 0 字节！            ← 还没给

第一次访问这块内存中的某个 4KB 页:
  虚拟地址空间:  这块 4KB 区域有映射了
  物理内存:      分配了 1 页 (4KB)          ← 才真正给，触发 page fault

最终: 进程实际只用到了这 16GB 中的 200MB
     → 物理内存也只消耗了 ~200MB
```

完整的时间线：

```
T1: malloc(16GB) → 成功返回，虚拟地址空间预留了 16GB 的地址范围
                    物理内存: 0 字节已分配

T2: ptr[0] = 42  → CPU 访问 ptr 指向的第一页
                   → MMU 查页表：发现该虚拟页不存在（P=0）
                   → 触发 page fault（缺页异常）
                   → 内核：分配一个 4KB 物理页，清零，更新页表
                   → 返回用户态，指令重试
                   → 写入成功
                   物理内存: +4KB

T3: 继续使用...   每访问一个新的 4KB 页，就多分配 4KB 物理内存
                   最终: 可能只用了几百 MB
```

### 原因 2：大部分映射是"空洞"

进程的 128TB 用户空间里，绝大多数虚拟地址范围内**什么都没有映射**——既没有文件映射，也没有匿名内存映射。

| 区域 | 大小 | 说明 |
|---|---|---|
| 代码段 | ~几MB | 可执行文件加载到内存的部分 |
| 数据段 + BSS | ~几MB | 全局和静态变量 |
| 堆 | 按需增长 | `malloc`/`new` 分配 |
| mmap 区 | 按需使用 | 动态库、大块分配、文件映射 |
| 栈 | 通常 ~8MB | 函数调用栈，按需增长 |
| 其余全部 | 约 127.9TB | **空洞，什么都没有映射** |

### 原因 3：页面交换（Swap）

即使所有进程使用的物理内存总和超过了 16GB，操作系统可以把不常用的页面**换出到磁盘**（swap 分区），把物理内存腾给活跃页面。

> ⚠️ 低延迟系统通常会关闭 swap，避免访问已换出的页面时触发毫秒级的磁盘 IO。

### 决定性因素：局部性原理（Locality of Reference）

**局部性原理是虚拟内存能够工作的理论基础**：

| 局部性类型 | 含义 | 例子 |
|---|---|---|
| **时间局部性** | 刚访问过的数据，短期内很可能再被访问 | 循环变量、热路径上的计数器 |
| **空间局部性** | 访问某个地址后，很可能访问它附近的地址 | 数组遍历、结构体字段访问、函数调用栈 |

正是因为程序在任意时刻**真正活跃使用的内存只占其总虚拟地址空间的一小部分**（这个活跃集合称为**工作集 Working Set**），操作系统才可以：

1. 给每个进程"夸大承诺"（overcommit）远大于物理内存的虚拟地址空间；
2. 只为实际被访问的页面分配物理内存；
3. 在不活跃页面和磁盘之间换入换出（如果需要 swap）。

```
进程分配了 16GB 虚拟内存，但工作集只有 200MB:

  ┌──────────────────────────────────────────────┐
  │  虚拟地址空间 (16GB 已分配)                    │
  │                                              │
  │  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │ ← 已分配但很少访问
  │  ░░░░████░░░░░░░██████░░░░░░░░░██░░░░░░░░░░ │ ← █ = 工作集 (活跃)
  │  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │    ░ = 已分配但冰冷
  │                                              │
  └──────────────────────────────────────────────┘
                         ↓
         物理内存只需 ~200MB 来支撑工作集
```

## 四、分页机制基础

### 4.1 什么是页（Page）？

物理内存被切分成固定大小的**页帧**（Page Frame），虚拟内存被切成同样大小的**页**（Page）。x86-64 上最常见的页大小是 **4KB**。

```
虚拟地址空间:                    物理内存:
┌─── 页 0 ───┐                 ┌─── 页帧 0 ───┐
├─── 页 1 ───┤     页表映射     ├─── 页帧 1 ───┤
├─── 页 2 ───┤  ═══════════>   ├─── 页帧 2 ───┤
├─── 页 3 ───┤                 ├─── 页帧 3 ───┤
├─── ... ────┤                 ├─── ... ──────┤
├─── 页 N ───┤                 ├─── 页帧 M ───┤
└────────────┘                 └──────────────┘

页表 = 一张"翻译字典"，把每个虚拟页号映射到物理页帧号
```

### 4.2 分页 vs 分段

| 特性 | 分段（旧方案） | 分页（现代方案） |
|---|---|---|
| 划分单位 | 可变大小的段 | 固定大小的页（通常 4KB） |
| 外部碎片 | 严重 | 无（所有页一样大） |
| 内部碎片 | 无 | 有（最后一页未用完） |
| 交换到磁盘 | 需要连续区域 | 任意页可单独交换 |
| x86-64 使用 | 主要用于权限控制（FS/GS 段寄存器） | 主要的内存管理机制 |

现代操作系统以分页为主，分段基本退化为权限隔离的辅助机制。

## 五、页表映射原理

### 5.1 页表项（PTE）的结构

每个虚拟页在页表里有一个**页表项**（PTE，Page Table Entry），64 位系统中通常是 8 字节：

```
64 位页表项 (PTE) 结构:

 63  62       52 51                               12 11      9 8 7 6 5 4 3 2 1 0
┌────┬──────────┬─────────────────────────────────┬──────────┬───┬─┬─┬─┬─┬─┬─┬─┐
│ NX │  (保留)  │   物理页帧号 (PFN) 40 bits      │  (保留)  │ G │ │D│A│ │ │W│P│
└────┴──────────┴─────────────────────────────────┴──────────┴───┴─┴─┴─┴─┴─┴─┴─┘
  不可执行           物理地址 >> 12                         忽略 脏 访 U 读 存
                                                                    问 S 写 在
                                                                        位
```

关键标志位：

| 标志 | 含义 |
|---|---|
| **P (Present)** | 0 = 该页不在物理内存（swap 中或从未分配），访问时触发 **page fault** |
| **R/W (Read/Write)** | 0 = 只读，1 = 可读写。写只读页触发保护异常 |
| **U/S (User/Supervisor)** | 0 = 仅内核可访问，1 = 用户态可访问 |
| **A (Accessed)** | CPU 访问过该页后硬件自动设为 1（用于页面换出决策——LRU 近似） |
| **D (Dirty)** | 该页被写入过，硬件自动设为 1（换出时需要写回磁盘；干净页直接丢弃） |
| **G (Global)** | 全局页，进程切换时不清除该 TLB 条目（内核页常用） |
| **NX (No-eXecute)** | 禁止在该页执行代码（安全特性，防 buffer overflow 执行 shellcode） |

### 5.2 为什么需要多级页表？

如果只用一级页表，管理 48 位虚拟地址空间、4KB 页：

```
虚拟地址空间: 2^48 = 256TB
页大小:       4KB = 2^12
页表项总数:   2^48 / 2^12 = 2^36 = 68,719,476,736 个
每项 8 字节:  68.7 × 10^9 × 8 = 549,755,813,888 字节 ≈ 512 GB

→ 每个进程 512GB 的页表！这比物理内存还大！
```

**所以采用多级页表**。核心思想：只在实际用到的地址范围创建对应级别页表，未用到的部分不分配。

### 5.3 四级页表结构

```
  ┌────────────┐         ┌────────────┐
  │   PML4     │         │   PDPT     │
  │ (Level 4)  │ ──────→ │ (Level 3)  │
  │ 512 entries│         │ 512 entries│
  └────────────┘         └────────────┘
       │                       │
       │ (未映射 → 空)          │  ...可以有多个 PDPT
       └─ 不分配下级表          │
                               ▼
                         ┌────────────┐
                         │    PD      │
                         │ (Level 2)  │
                         │ 512 entries│
                         └────────────┘
                               │
                               ▼
                         ┌────────────┐
                         │    PT      │
                         │ (Level 1)  │
                         │ 512 entries│
                         └────────────┘
                               │
                               ▼
                         ┌────────────┐
                         │  物理页帧   │
                         │   4KB      │
                         └────────────┘
```

节省空间的原理：

```
                    单级页表:
                    所有虚拟页都需要一个 entry
                    256TB / 4KB = 6.87×10¹⁰ 个 entry
                    每个 8 字节 = 512GB (不可接受!)

                    4级页表:
                    只为实际用到的地址范围创建中间表

进程实际只用 200MB (分布在少数地址范围内):
                    ┌──────────────────────┐
                    │ PML4 (1 页, 4KB)     │ ← 必须存在
                    ├──────────────────────┤
                    │ PDPT (几页, 几十KB)   │ ← 只在有映射的 PML4 entry 下创建
                    ├──────────────────────┤
                    │ PD (几十页, 几百KB)   │ ← 只在有映射的 PDPT entry 下创建
                    ├──────────────────────┤
                    │ PT (几千页, ~几MB)    │ ← 只在有映射的 PD entry 下创建
                    └──────────────────────┘
                    总计: ~几 MB 的页表开销（vs 512GB）
```

### 5.4 虚拟地址的结构

以 4KB 页为例，x86-64 的 48 位虚拟地址被切分成 5 段：

```
64位虚拟地址 (实际有效位 48位):

 63  48 47          39 38              30 29              21 20              12 11           0
┌──────┬──────────────┬──────────────────┬──────────────────┬──────────────────┬──────────────┐
│ 符号  │   PML4 索引   │  PDPT 索引        │   PD 索引         │   PT 索引         │  页内偏移     │
│ 扩展  │  (9 bits)     │  (9 bits)         │  (9 bits)         │  (9 bits)         │  (12 bits)    │
└──────┴──────────────┴──────────────────┴──────────────────┴──────────────────┴──────────────┘
  bit63  bits 47..39    bits 38..30         bits 29..21         bits 20..12         bits 11..0

为什么每级索引是 9 bits？
  每级页表: 512 entries = 2^9 → 9 bits
  每个 entry: 8 bytes
  每级页表大小: 512 × 8 = 4096 bytes = 刚好 1 个 4KB 页
```

各段作用：

| 段 | 位数 | 作用 |
|---|---|---|
| 符号扩展 | 16 bits | 确保用户空间与内核空间地址不混淆 |
| PML4 索引 | 9 bits | 在 512 个 PML4 entry 中选择一个 |
| PDPT 索引 | 9 bits | 在选中的 PDPT 中选一个 entry |
| PD 索引 | 9 bits | 在选中的 PD 中选一个 entry |
| PT 索引 | 9 bits | 在选中的 PT 中选一个 entry → 物理页帧号 |
| 页内偏移 | 12 bits | 在 4KB 页内的具体字节偏移 (0–4095) |

### 5.5 四级页表翻译的完整流程

```
虚拟地址: 0x00007f00 1234 5678
         │
         │ 1. 拆解为 5 个字段
         ▼
  ┌──────────┬──────────┬──────────┬──────────┬──────────────┐
  │ PML4 idx │ PDPT idx │  PD idx  │  PT idx  │  offset      │
  │  9 bits  │  9 bits  │  9 bits  │  9 bits  │  12 bits     │
  └──────────┴──────────┴──────────┴──────────┴──────────────┘

2. CR3 ──→ PML4 表物理基址
              │
              ├─ PML4[PML4_idx] → PDPT 物理基址
              │                     │
              │                     ├─ PDPT[PDPT_idx] → PD 物理基址
              │                     │                     │
              │                     │   (entry为空 → page fault)
              │                     │   (entry为空 → page fault)
              │                     │                     ├─ PD[PD_idx] → PT 物理基址
              │                     │                     │                   │
              │                     │                     │                   ├─ PT[PT_idx]
              │                     │                     │                   │   → PFN (物理页帧号)
              │                     │                     │                   │
              │                     │                     │                   │   (P=0 → page fault)
              │                     │                     │                   │
              │                     │                     │                   ▼
              │                     │                     │            物理地址 = PFN × 4096 + offset

3. 每一步涉及一次内存读取:
   CR3 → PML4[..] → PDPT[..] → PD[..] → PT[..]
   共 4 次内存访问来定位物理页帧号
```

### 5.6 页表带来的性能问题

每次内存访问都要先做页表翻译。如果每次都走 4 级遍历，一次 `mov rax, [ptr]` 需要：

| 操作 | 次数 |
|---|---|
| 页表遍历（4 次内存读） | 4 次 |
| 实际数据访问 | 1 次 |
| **总计** | **5 次内存访问** |

这就是 **TLB（Translation Lookaside Buffer）** 存在的根本原因。

## 六、TLB：硬件加速的地址翻译缓存

### 6.1 TLB 是什么？

TLB 是 CPU 内部的一个小型硬件缓存（CAM，Content-Addressable Memory），专门存储最近翻译过的"虚拟页号 → 物理页帧号"映射。

```
                ┌──────────────────┐
                │      TLB         │  硬件缓存，几十到几千条条目
   虚拟地址 ──→ │ vpn → pfn 映射   │ ──→ 物理地址 (命中: ~1 个周期)
                │ 命中: ~1 周期     │
                │ 未命中: 查页表    │
                └──────────────────┘
                        │
                   未命中时:
                        ↓
                ┌──────────────────┐
                │  页表遍历 (PTW)   │  MMU 自动做 4 级页表遍历
                │  4 次内存读取     │  完成后将结果缓存到 TLB
                │  数十~数百周期     │
                └──────────────────┘
```

### 6.2 TLB 各层级延迟

现代 CPU 的 TLB 也是分级的：

| 层级 | 典型条目数 | 延迟 |
|---|---|---|
| L1 TLB（指令） | ~64–128 条目 | 1 周期 |
| L1 TLB（数据） | ~64–128 条目 | 1 周期 |
| L2 TLB（统一） | ~512–2048 条目 | ~5–10 周期 |
| 页表遍历（PTE 在 L1 缓存） | — | ~20–30 周期 |
| 页表遍历（PTE 在 L2 缓存） | — | ~50 周期 |
| 页表遍历（PTE 在 L3 缓存） | — | ~100–200 周期 |
| 页表遍历（PTE 在 DRAM） | — | ~300+ 周期 |

### 6.3 TLB 命中率至关重要

以一个 4KB 页覆盖的 TLB 条目为例：

| 页大小 | 单 TLB 条目覆盖范围 | L1 TLB (64 条目) 覆盖范围 |
|---|---|---|
| 4KB | 4KB | 256KB |
| 2MB | 2MB | 128MB |
| 1GB | 1GB | 64GB |

由此可见，TLB 条目非常珍贵。低延迟系统常用**大页（Huge Pages）**扩大单条 TLB 条目的覆盖范围：

```
普通 4KB 页:
  访问 1GB 数据 = 262,144 个页 = 262,144 个 TLB 条目（远超 TLB 容量）
  → 大量 TLB miss，每次访问都可能触发页表遍历

2MB 大页:
  访问 1GB 数据 = 512 个页 = 512 个 TLB 条目
  → 大部分可以命中 TLB，页表遍历次数大大减少

1GB 巨页:
  访问 1GB 数据 = 1 个页 = 1 个 TLB 条目
  → 100% TLB 命中
```

### 6.4 进程切换时 TLB 会怎样？

```
进程 A 运行中:
  TLB 中填充的都是 进程 A 的映射

操作系统切换到 进程 B:
  1. 加载进程 B 的 CR3（指向 B 的 PML4 表）
  2. CR3 被修改时，CPU 自动刷新整个 TLB（flush）
     （全局页 G=1 的条目除外，通常是内核页）
  3. 进程 B 开始执行，TLB 为空，每次访问都走页表遍历
  4. TLB 逐渐"预热"，命中率回升

线程亲和性的另一个好处：
  线程固定在同一个核心上运行，减少切换时的 TLB 刷新次数
```

## 七、完整流程串联

以进程访问 `0x7f1234ABCD` 为例，从 CPU 指令到物理内存读取的全过程：

```
1. CPU 执行: mov rax, [0x7f1234ABCD]
   
2. MMU 拦截这个虚拟地址，先查 TLB:
   ┌─ TLB 命中？
   │  是 → 直接得到物理地址，跳到步骤 8
   │  否 → 继续步骤 3（TLB miss）
   └─

3. 页表遍历 (4 次内存读):
   CR3 → PML4[bits 47:39] → PDPT[bits 38:30] → PD[bits 29:21] → PT[bits 20:12]
   
4. 读取 PTE，检查 P (Present) 标志:
   
   ┌─ P=1, 页在物理内存:
   │   继续步骤 5
   │
   ├─ P=0, 这是合法但从未被访问的虚拟地址:
   │   1. 触发 page fault（缺页异常）
   │   2. CPU 切换到内核态，保存上下文
   │   3. 内核：分配一个 4KB 物理页（从 buddy allocator）
   │   4. 新页清零（如果是匿名映射）
   │   5. 更新 PTE：设置 PFN、P=1、R/W、U/S 等
   │   6. 返回用户态，指令重试
   │   物理内存: +4KB
   │
   ├─ P=0, 这是换出到 swap 的页面:
   │   1. 触发 page fault
   │   2. 内核：从 swap 分区/文件读回物理内存
   │   3. 更新 PTE
   │   4. 返回用户态，指令重试
   │   延迟: 毫秒级（磁盘IO）
   │
   └─ 这是非法访问（从未 mmap/malloc/分配栈）:
       1. 触发 page fault
       2. 内核：判断为无效访问
       3. 发送 SIGSEGV 信号给进程
       4. 进程收到段错误，默认行为：终止
   
5. 检查权限:
   ┌─ 写只读页 → 保护异常
   └─ 执行 NX 页 → 保护异常

6. 将翻译结果 (PFN) 载入 TLB

7. 更新 PTE 中的 A (Accessed) 位（硬件自动完成）
   如果是写操作，同时更新 D (Dirty) 位

8. 物理地址 = PFN × 4096 + offset(vaddr的低12位)
   = 0x3a2f1000 + 0xBCD
   = 0x3a2f1BCD

9. CPU 从物理地址 0x3a2f1BCD 读取数据

10. 完成指令，rax 寄存器得到值
```

## 八、大页（Huge Pages）

### 8.1 大页的级别

| 页大小 | CPU 支持 | 页表级数 | 单页覆盖范围 |
|---|---|---|---|
| 4KB（标准页） | 所有 x86-64 | 4 级 | 4KB |
| 2MB（大页） | 所有现代 x86-64 | 3 级（跳过 PT） | 2MB |
| 1GB（巨页） | 较新的 x86-64 | 2 级（跳过 PT+PD） | 1GB |

### 8.2 大页的优缺

| 优势 | 劣势 |
|---|---|
| TLB 命中率大幅提高（一个条目覆盖更多内存） | 内部碎片（申请 3MB 配 2MB+4KB×256 或浪费 1MB 巨页） |
| 减少页表遍历级数（4 级→3 级或 2 级） | 分配失败率高（需要连续物理内存） |
| 减少 page fault 次数（同数据量下页更少） | 交换到磁盘困难（很多 swap 实现不支持大页） |
| 减少页表内存开销 | 需要提前配置和预留 |

### 8.3 低延迟系统的大页配置

```bash
# 查看大页信息
cat /proc/meminfo | grep Huge

# 预留 1024 个 2MB 大页 (共 2GB)
echo 1024 > /proc/sys/vm/nr_hugepages

# 或者在启动时配置
# GRUB_CMDLINE_LINUX="hugepages=1024"

# 程序中使用大页
# mmap 时使用 MAP_HUGETLB 标志
void* ptr = mmap(NULL, 2*1024*1024, PROT_READ|PROT_WRITE,
                 MAP_PRIVATE|MAP_ANONYMOUS|MAP_HUGETLB, -1, 0);
```

## 九、关键概念速查

| 概念 | 一句话解释 |
|---|---|
| 虚拟内存 | 进程看到的地址空间，通过页表翻译为物理地址 |
| 物理内存 | 真实的 RAM 芯片上的存储单元 |
| 页（Page） | 虚拟内存的最小管理单元，通常是 4KB |
| 页帧（Page Frame） | 物理内存的最小管理单元，大小与页相同 |
| 页表（Page Table） | 虚拟页号 → 物理页帧号的映射表 |
| PTE | 页表项，8 字节，含 PFN + 标志位 |
| MMU | CPU 内的内存管理单元，负责地址翻译 |
| TLB | 翻译后备缓冲区，缓存最近使用的页表映射 |
| 缺页异常（Page Fault） | 虚拟页无对应物理页时触发，由内核处理 |
| 工作集（Working Set） | 进程在任意时刻真正活跃使用的内存集合 |
| 局部性原理 | 程序倾向于在短时间内反复访问有限的内存区域 |
| Lazy Allocation | 分配虚拟地址时只记账，访问时才分配物理页 |
| 多级页表 | 用树状结构取代单级大表，未映射的区域不分配表 |
| CR3 | x86 控制寄存器，指向当前进程的 PML4 物理地址 |
| 大页（Huge Pages） | 2MB/1GB 的大页面，减少 TLB miss 和页表遍历 |

## 十、常见思考题

**1. 32 位系统最多支持 4GB 物理内存，为什么？**

32 位地址线 = 2^32 = 4GB，CPU 能产生的物理地址范围最大就是 4GB。PAE（Physical Address Extension）可以扩展到 64GB，但单个进程仍只能看到 4GB（内核通过额外页表级管理）。

**2. 64 位系统为什么实际只用了 48 位？**

256TB（2^48）已经足够大，再多级页表会增加。而且当前硅片上的物理地址线也只有 ~48 位左右。未来 5 级页表（57 位地址）已进入 Linux 内核。

**3. 为什么说缓存友好的代码 TLB 也友好？**

缓存友好通常意味着连续访问、局部性高，这同样意味着：活跃的页数量少 → TLB 覆盖好 → TLB miss 少。缓存友好和 TLB 友好的代码特征高度重合。

**4. 关闭 swap 后，虚拟内存的优势还在吗？**

在。即使关闭 swap：
- 按需分页仍然有效（未访问的页不分配物理内存）；
- 进程地址空间隔离仍然有效（安全）；
- 共享库映射仍然有效（多个进程共享同一物理页的 libc）；
- 内存映射文件仍然有效（`mmap` 文件到地址空间）。

**5. 为什么 C++ `new` 分配 1MB 和分配 100MB，页面分配过程有区别吗？**

有区别：
- 1MB（≤ 128KB 阈值）：走 `brk()` 管理的堆，从堆的 top chunk 切割，页面按需分配；
- 100MB（> 128KB 阈值）：直接用 `mmap()` 独立映射，释放时 `munmap()` 整体归还。
- 另外 `mmap` 大块时使用 THP（Transparent Huge Pages）可能自动获得 2MB 大页。
