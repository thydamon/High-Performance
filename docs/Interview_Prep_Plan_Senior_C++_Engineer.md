### 第 1 周：C++ 深度系统化

> **核心目标**：建立 C++ 面试知识体系框架，从编译原理到现代特性全覆盖。

#### Day 1：编译链接全流程与内存布局

- [ ] **编译与链接全流程**
  - 预处理 → 编译 → 汇编 → 链接（静态链接 vs 动态链接）
  - 符号表、重定位、GOT/PLT 概念
  - `-fPIC`、`-Wl,-rpath` 等关键编译选项
  - 常见编译错误与排查方法
- [ ] **内存模型与内存布局**
  - 虚地址空间分布：Text / Data / BSS / Heap / Stack / mmap
  - 对齐（Alignment）与填充（Padding）
  - `sizeof` 常见陷阱、空类/虚继承的大小
  - 字节序（Big/Little Endian）

**📖 推荐练习：**
- 手写一个 linker script 理解段布局
- 用 `objdump`、`readelf`、`nm` 分析编译产物

#### Day 2：面向对象核心机制深入

- [ ] **虚函数与多态**
  - 虚函数表（vtable）布局与虚函数调用开销
  - 单继承 / 多重继承 / 虚继承下的 vtable 布局差异
  - `dynamic_cast` 实现原理与性能影响（指针 vs 引用）
  - RTTI（运行时类型识别）机制与 `typeid`
  - 纯虚函数与抽象类的编译器约束
- [ ] **构造与析构**
  - 构造函数中的虚函数调用行为
  - 虚析构函数的必要性
  - 异常安全与 RAII 模式（回顾及最佳实践）
  - `= default` / `= delete` / Rule of Five / Rule of Zero

**📖 推荐资料：**
- 《Inside the C++ Object Model》— Stanley Lippman（第 1、3、4 章）

#### Day 3：C++11/14/17 关键特性面试复习

- [ ] **移动语义与智能指针**
  - 右值引用、`std::move`、完美转发（`std::forward`）的底层原理
  - 引用折叠规则
  - `unique_ptr` / `shared_ptr` / `weak_ptr` 实现原理与使用场景
  - `shared_ptr` 的控制块结构与线程安全性
  - `weak_ptr` 解决循环引用
- [ ] **Lambda 与函数对象**
  - Lambda 闭包捕获（值捕获 / 引用捕获 / 初始化捕获 C++14）
  - 泛型 Lambda（C++14）
  - `std::function` 的类型擦除实现原理
  - `std::bind` vs Lambda 对比

#### Day 4：C++17/20 现代特性

- [ ] **C++17 关键特性**
  - `std::variant` / `std::optional` / `std::any` —— 每种的使用场景
  - `std::string_view` —— 零拷贝字符串引用
  - 结构化绑定（Structured Bindings）
  - `if constexpr` —— 编译期条件分支
  - 折叠表达式（Fold Expressions）
  - 类模板参数推导（CTAD）
- [ ] **C++20 关键特性**
  - Concepts —— 约束模板参数，提升错误信息可读性
  - Ranges —— 管道式集合操作，惰性求值
  - Coroutines —— `co_await` / `co_yield` / `co_return` 异步编程
  - `constexpr` 增强（`constexpr new` / `constexpr string` / `constexpr vector`）
  - `consteval` / `constinit`
  - Three-Way Comparison（`<=>`，Spaceship Operator）

**📖 推荐资料：**

#### Day 5：模板元编程基础 + STL 源码剖析

- [ ] **模板基础面试要点**
  - 模板特化（全特化 / 偏特化）

#### Day 1：半导体产业链全景认知

- [ ] **半导体产业链概览**
  - 芯片设计（Fabless）→ 晶圆制造（Foundry）→ 封装测试（OSAT）全流程
  - 理解 IC 设计公司（如高通、英伟达、海思）vs 制造厂（台积电、中芯国际）vs 封测厂（日月光、长电科技）
  - 摩尔定律放缓后的行业趋势：先进封装（Chiplet/3D IC）、异构集成
- [ ] **ATE（自动测试设备）基础**
  - ATE 是什么：用于芯片量产测试的自动化设备，确保每颗芯片出厂达标
  - 为什么需要 ATE：人工测试无法满足百万/亿级出货的质量与成本要求
  - 主要厂商：Teradyne（泰瑞达）、Advantest（爱德万）、National Instruments（NI）、华峰测控、长川科技
  - ATE 系统架构：测试头（Test Head）→ 信号源/测量模块 → DUT 接口板（DIB/Load Board）→ Handler/Prober 对接
- [ ] **关键术语扫盲**：CP（Chip Probe 晶圆测试）、FT（Final Test 成品测试）、DUT（Device Under Test）、Pin Electronics、Pattern Generator、STDF 数据格式

#### Day 4：C# 与 C++ 混合编程（下）—— C++/CLI 与 COM

- [ ] **C++/CLI（托管 C++）**

  - `#pragma managed` / `#pragma unmanaged`
  - 混合程序集的编译与部署

- [ ] **COM 互操作（了解）**

  - C++ 实现 COM 组件，C# 通过 RCW 调用

- [ ] **方案对比总结**

| 方案 | 复杂度 | 性能 | 适用场景 |
|------|--------|------|---------|
| P/Invoke | 中 | 高（有封送开销） | 调用 C 风格导出函数 |
| C++/CLI | 高 | 最高 | 复杂对象模型互操作 |
| COM 互操作 | 高 | 中 | 已有 COM 组件复用 |

#### 简历要点 2：基于内存池和零拷贝的数据流转方案，关键路径延迟降低 50%

| 面试官可能这样问 | 回答要点 |
|-----------------|---------|
| "延迟降低 50%——before/after 的具体数据是多少？怎么测量的？" | 准备具体数据：优化前 P99 延迟 X μs，优化后 Y μs。测量工具：自行实现的计时埋点 + `perf` 火焰图验证 |
| "内存池是怎么设计的？分层了吗？" | 三层设计：Thread Cache（无锁）→ Central Cache（自旋锁）→ Page Heap（系统分配）。每层职责、数据结构（Free List / Span） |

| "从开发转到项目经理，最大的挑战是什么？" | 从"管好自己的代码"到"管好团队的交付"——进度管理、风险预判、跨部门协调 |
| "你用什么方法管理项目进度和风险？" | 里程碑管理——将项目拆分为可验收的阶段交付物。风险预警：每周风险评估会，红/黄/绿三级预警 |
| "遇到过最棘手的一次项目危机是什么？怎么处理的？" | 准备一个具体案例（如：UAT 阶段发现关键性能问题、或第三方接口变更...） |

### 3.4 跨进程/跨语言通信中间件（恒生）

#### 简历要点 12：C++ ↔ Java 跨语言通信

| 面试官可能这样问 | 回答要点 |
|-----------------|---------|
| "C++ 和 Java 之间怎么通信的？你设计了什么方案？" | Socket + 自定义二进制协议（性能优先场景）；共享内存 + JNI（超低延迟场景）。序列化格式用自定义结构体（因为比 Protobuf 更轻量） |
| "跨语言通信最大的难点是什么？" | 数据表示差异（C++ struct 内存布局 vs Java 对象字段偏移）、字节序一致性、字符串编码（C++ 用 UTF-8，Java 内部用 UTF-16） |
| "为什么不直接用 gRPC/Thrift？" | gRPC 当时不够成熟（2019年），且自定义协议更轻量——我们的场景是内部系统间通信，不需要 gRPC 的 HTTP/2 和跨语言生态。但后来在新项目中引入了 Protobuf |
| "异常预警时效提升 40% 是怎么做到的？" | 之前是定时轮询（5s 间隔），改为事件驱动推送（Socket 长连接 + 异步回调），异常到达即刻通知 |
| "如果让你重新设计这个通信中间件，你会怎么改进？" | 引入 Protobuf 替代自定义二进制协议（降低维护成本）；引入 gRPC Stream 替代自建 Socket 协议（减少代码量）；引入服务注册发现（不用硬编码 IP） |

### 3.5 AI 辅助开发工作流（恒生）

#### 简历要点 13：对抗式多智能体 + 工程化解决 AI 幻觉

| 面试官可能这样问 | 回答要点 |
|-----------------|---------|
| "对抗式多智能体具体是怎么工作的？" | 一个 Agent 生成代码 → 另一个 Agent 做 Code Review/攻击（试图找到 bug）→ 第三个 Agent 修复 → 循环直到审查通过。利用了 LLM 之间的相互纠错能力 |
| "AI 幻觉问题你是怎么解决的？" | 分层策略：① 输入层——RAG 提供上下文（项目代码片段+API 文档），缩小生成范围；② 验证层——编译检查+单元测试自动运行，语法错误立刻暴露；③ 审查层——对抗 Agent 二次确认语义正确性 |
| "实际效果怎么样？有没有量化数据？" | 准备具体数据：单元测试生成覆盖率从手工的 X% 提升到 AI 辅助的 Y%，Code Review 发现的低级错误减少 Z% |
| "团队推广遇到了什么阻力？" | 初期：老员工质疑 AI 代码质量 → 用数据说话（AI 生成代码的 Bug 率 vs 人工代码）；中期：Code Review 工作量增加 → 引入自动审查 Agent 分担 |
| "你认为 AI 辅助开发的极限在哪里？什么场景不适合？" | 不适合：安全关键系统（如交易核心引擎）、需要深度领域知识的代码（如复杂金融算法）、极高性能敏感的代码（AI 对缓存/流水线优化理解不足）。适合：CRUD、单元测试、文档生成、Code Review |

### 3.6 架构能力 & 技术管理（综合）

#### 简历要点 14：主导制定技术标准、代码规范、CI/CD 流程

## 四、快速参考：核心知识点卡片

### C++ 内存模型速查
```
高地址: 命令行参数/环境变量
        ↓
        栈（Stack）—— 向下增长
        ↓
        ↓ (未分配区域)
        ↓
        堆（Heap）—— 向上增长
        .bss（未初始化全局/静态变量）
        .data（已初始化全局/静态变量）
        .rodata（只读数据）
低地址: .text（代码段）
```

### 锁性能对比速查
| 锁类型 | 开销 | 适用场景 |
|--------|------|---------|
| `std::mutex` | 中等（~25ns 无竞争） | 临界区较长 |
| `std::shared_mutex` | 较高 | 读多写少 |
| Spinlock | 低（~5-10ns 无竞争） | 临界区极短（几个指令） |
| CAS 原子操作 | 最低（~1ns） | 单变量原子更新 |
| RCU（Read-Copy-Update）| 读几乎为 0 | 读极多写极少 |

### IPC 通信性能对比速查
| 方式 | 延迟 | 吞吐 | 复杂度 | 跨语言 |
|------|------|------|--------|--------|
| 共享内存 | 最低（~100ns） | 最高（GB/s） | 高 | 需序列化 |
| Unix Socket | ~10μs | 中等 | 中 | 天然支持 |
| TCP Socket（本地）| ~20μs | 中等 | 低 | 天然支持 |
| 管道 | ~5μs | 低 | 低 | 天然支持 |
| 消息队列 | ~5μs | 低 | 低 | 需序列化 |
